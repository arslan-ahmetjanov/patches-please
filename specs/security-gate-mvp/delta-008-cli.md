# Delta-спека 008: CLI-клиент для CI

Статус: принята 22.11.2026. Дополняет [spec.md](spec.md), не заменяя её.
Основание — задачи T-026, T-027, T-028; решение от 22.11.2026 о едином клиенте.

Нумерация начинается с FR-031: FR-030 занят [delta-007-scanners.md](delta-007-scanners.md).

## Зачем

FR-019 и FR-020 требуют одинакового поведения от двух CI: один и тот же вызов
API, код выхода 0 при `pass` и 1 при `fail`. В плане (раздел «Архитектура»)
обёртки описаны как «три вызова: старт, поллинг, выход с кодом» — по 30 строк
на каждого провайдера. Это две независимые реализации одного протокола на двух
разных шеллах. Расхождение между ними обнаружится только тестом T-028, то есть
после того, как обе написаны.

План (раздел «Команды») уже фиксировал команду `app.cli scan`, но требования на
неё в `spec.md` нет: ни интерфейса, ни кодов выхода, ни поведения при таймауте.
Без этого T-026 и T-027 пришлось бы писать дважды, а T-028 проверял бы
совпадение двух самодельных поллингов.

Эта delta-спека делает CLI единственной реализацией протокола CI. Обёртки
провайдеров становятся установкой клиента и одним вызовом. Поведение сервиса не
меняется: API остаётся тем же, новых эндпоинтов нет.

## Требования

| ID | Требование (EARS) | Приоритет | Критерий приёмки (Дано — Когда — Тогда) |
| --- | --- | --- | --- |
| FR-031 | Когда клиент запущен с адресом сервера, токеном проекта, коммитом, ссылкой и провайдером, он ДОЛЖЕН создать прогон через `POST /api/v1/scans` и получить его идентификатор. | must | Дано сервер доступен и токен верен; Когда клиент запущен с полным набором аргументов; Тогда отправлен один `POST`, получен `scan_id`, клиент напечатал его в человекочитаемом режиме. Дано сервер вернул `200` с существующим прогоном вместо `202`; Когда клиент получил ответ; Тогда он использует возвращённый идентификатор и не считает это ошибкой. |
| FR-032 | Когда указан флаг ожидания, клиент ДОЛЖЕН опрашивать `GET /api/v1/scans/{id}` до терминального статуса или истечения таймаута. | must | Дано прогон в статусе `queued` или `running`; Когда идёт ожидание; Тогда клиент опрашивает сервер с заданным интервалом и завершает ожидание при `done` или `error`. Дано таймаут истёк; Когда прогон всё ещё не терминальный; Тогда ожидание прекращается и клиент завершается кодом 5, а не продолжает опрос. |
| FR-033 | Клиент ДОЛЖЕН завершаться кодом 0 при вердикте `pass` и кодом 1 при вердикте `fail`; остальные исходы ДОЛЖНЫ иметь различимые коды. | must | Дано прогон с вердиктом `fail`; Когда клиент дождался завершения; Тогда код выхода 1 (FR-020). Дано прогон с вердиктом `pass`; Когда клиент дождался завершения; Тогда код выхода 0. Дано каждый из исходов «нет токена», `401`, `status=error`, таймаут, сервер недоступен; Когда клиент завершился; Тогда код входит в документированную таблицу и отличен от 0 и 1. |
| FR-034 | Клиент НЕ ДОЛЖЕН выводить токен проекта ни в одном режиме, включая сообщения об ошибках и трассировки. | must | Дано клиент запущен с `--token` и с `--verbose`; Когда вывод захвачен целиком; Тогда значение токена не встречается ни в stdout, ни в stderr (NFR-004). Дано сервер ответил `401`; Когда клиент напечатал ошибку; Тогда в ней есть код ответа и подсказка про токен, но не его значение. |
| FR-035 | Клиент ДОЛЖЕН поддерживать машиночитаемый вывод и печатать ссылку на отчёт в человекочитаемом режиме. | should | Дано клиент запущен с флагом машиночитаемого вывода; Когда прогон завершён; Тогда stdout содержит один JSON-объект прогона без посторонних строк. Дано человекочитаемый режим; Когда прогон завершён; Тогда напечатаны вердикт, число находок по severity и адрес отчёта. |
| FR-036 | Если сервер ответил `5xx` или соединение не установлено, клиент ДОЛЖЕН повторить запрос с паузой и в итоге завершиться кодом сетевой ошибки. | must | Дано сервер отвечает `503`; Когда клиент опрашивает статус; Тогда повторы выполняются с нарастающей паузой в пределах общего таймаута. Дано повторы исчерпаны; Когда клиент завершился; Тогда код 6 и сообщение с последней ошибкой. Дано ответ `4xx`; Когда клиент его получил; Тогда повтора нет. |
| FR-037 | Клиент НЕ ДОЛЖЕН вычислять или переопределять вердикт: единственный источник вердикта — ответ API. | must | Дано сервер вернул `done` с вердиктом `pass` при наличии находок `critical` в ответе; Когда клиент завершился; Тогда код 0, потому что клиент не пересчитывает политику. |
| NFR-007 | Клиент ДОЛЖЕН запускаться без системных зависимостей, кроме Python 3.12, и не требовать доступа к базе, Redis или файловой системе проекта. | should | Дано чистое окружение с Python 3.12; Когда клиент запущен против доступного API; Тогда он работает, и в его процессе нет обращений к `DATABASE_URL` и к каталогу репозитория. |

## Решения и детали

- **Где живёт код.** `patches_please/cli.py`, точка входа `patches-please`
  в `[project.scripts]`. Тот же модуль вызывается как
  `python -m patches_please.cli`, чтобы работал запуск без установки пакета.
  Каталог `app/` переименовывается в `patches_please/` задачей T-034: пакет с
  именем `app` на верхнем уровне wheel конфликтует с чужими пакетами.
- **Зависимости.** Клиенту нужен только `httpx`. Он переезжает из
  `dependency-groups.dev` в `project.dependencies`: пакет один, отдельная
  клиентская сборка для MVP избыточна. Плата — установка полного набора
  зависимостей в CI, около 15 секунд.
- **Аргументы.** `--server` (по умолчанию из `PATCHES_PLEASE_URL`, иначе
  `http://localhost:8000`), `--token` (иначе `PATCHES_PLEASE_TOKEN`),
  `--provider github|gitlab`, `--commit`, `--ref`, `--wait`, `--timeout`
  (по умолчанию 900 с, с запасом к NFR-002), `--interval` (5 с), `--json`,
  `--fail-on-degraded`. Флаг важнее переменной окружения: в CI удобнее
  подставить секрет, но при отладке нужно переопределить.
- **Провайдер обязателен.** FR-019 требует передавать провайдера, а угадывать
  его по переменным окружения раннера — скрытая логика, которая ломается при
  смене образа. Нет `--provider` — код 2.
- **Таблица кодов выхода.** 0 — `pass`; 1 — `fail`; 2 — ошибка аргументов;
  3 — `401`/`403`; 4 — `status=error`; 5 — таймаут ожидания; 6 — сеть или
  `5xx` после повторов. Коды 0 и 1 зафиксированы FR-020 и не могут меняться;
  остальные выбраны так, чтобы CI-лог отличал «код плохой» от «сервис сломан».
- **Идемпотентность.** План (раздел «Нефункциональные аспекты») обещает
  возвращать существующий прогон при повторном `commit_sha`. Клиент принимает
  и `202`, и `200`, и не создаёт второй прогон повторным вызовом.
- **Повторы.** Повторяются только `5xx` и сетевые ошибки при опросе статуса.
  `4xx` не повторяются: повтор запроса с тем же неверным токеном ничего не
  изменит. Общий таймаут `--timeout` ограничивает и повторы, и ожидание.
- **Вывод.** Человекочитаемый режим — три строки: вердикт, находки по severity,
  адрес отчёта. Машиночитаемый — ровно один JSON-объект в stdout, диагностика
  в stderr. Цвет и рамки только при TTY: в CI-логе escape-последовательности
  мусорят.
- **Без интерактива.** Никаких подтверждений и запросов ввода: клиент работает
  в неинтерактивном раннере. Отсутствие токена — ошибка, а не приглашение
  ввести его.
- **Границы.** Клиент не клонирует репозиторий, не запускает сканеры, не
  применяет политику и не считает вердикт (FR-037). Всё это сервис.

## Ограничения

- Клиент не умеет запускать прогон без провайдера и без `--commit`: локальный
  «прогон всего» — это `POST /scans` с сервера, а не сценарий CI.
- `--fail-on-degraded` только передаёт серверу намерение; итоговый вердикт
  считает политика проекта (FR-013). Если политика `fail-open`, клиент вернёт
  0 даже при флаге — это ожидаемо и фиксируется в документации.
- Клиент не проверяет TLS-сертификаты нестандартным способом: самоподписанный
  стенд требует `--insecure` или системного доверия. Флаг появится, только если
  понадобится на демо-стенде.
- Коды 2–6 не входят в контракт OpenAPI: это поведение клиента, а не сервера.
  Контракт от этой дельты не меняется.
- Клиент не публикуется на PyPI: установка идёт из репозитория или из wheel,
  собранного T-035.
