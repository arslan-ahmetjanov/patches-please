# Спека: Security Gate — V1

## ПРЕДПОЛАГАЮ

Всё, что ниже, я додумал сам. Поправь сейчас — иначе иду с этим.

- **Развёртывание.** Локально через Docker Compose: API, PostgreSQL, воркер, веб-интерфейс. Без облачных сервисов — чтобы система запускалась на вузовской машине и на демо-стенде на защите.
- **Стек.** Python 3.12 + FastAPI, PostgreSQL 16, SQLAlchemy + Alembic, фоновые задачи через очередь. Веб — простой серверный интерфейс: список проектов, страница проекта с трендом, страница прогона с находками, формы политики и исключений. Без SPA и отдельной сборки фронтенда.
- **Сканеры.** Semgrep OSS (SAST), Gitleaks (секреты), Trivy (уязвимые зависимости и образы). Все три — open source, запускаются локально.
- **CI.** Поддерживаем два провайдера: GitHub Actions — основной, на нём демонстрация и приёмка; GitLab CI — второй, с тем же контрактом. Оба — тонкие обёртки над одним REST API, бизнес-логика живёт в сервисе.
- **Аутентификация.** Локальные учётные записи и API-токены. Без SSO, LDAP и внешних провайдеров.
- **Арендатор.** Одна организация, несколько проектов. Мультитенантности нет.
- **Объект демонстрации.** Собственный репозиторий с намеренно внедрёнными уязвимостями. Данные работодателя не используются ни на одном этапе.
- **Экономическая часть ВКР** считается только на демо-стенде и явно перечисленных допущениях (ставка часа, число релизов, стоимость инцидента). Закрытые данные работодателя не используются ни на одном этапе.

## Проблема

Проверки безопасности делаются вручную и нерегулярно: перед релизом, по просьбе, иногда — после инцидента. Разработчик узнаёт об уязвимости поздно, когда переделка стоит дорого, а безопасник тратит время на однотипный просмотр изменений вместо разбора сложных случаев.

Инструменты проверки при этом есть, но они разрознены: у каждого свой формат отчёта, свои правила запуска, свой порог срабатывания. Встроить это в пайплайн без собственного оркестратора и единой политики невозможно, поэтому на практике всё сводится к запуску «когда вспомнили».

## Источник темы

реализации. Чтобы не совпадать с одноимённым коммерческим продуктом VK Cloud,
продукт называется **Patches, Please** (T-034), а «Security Gate» остаётся в
спеке и в тексте ВКР только как обозначение класса. Наименование темы ВКР при
этом не меняется.

## Цель и метрика

Разработчик получает вердикт по безопасности автоматически и на каждом изменении, до мержа, а не после релиза.

Метрики приёмки V1:

- 100% изменений в демо-репозитории проходят проверку автоматически, без ручного запуска.
- Время от появления коммита до вердикта — не более 10 минут для репозитория до 100 тыс. строк.
- Новая критическая находка блокирует пайплайн в 100% случаев, если она не покрыта действующим исключением.
- Отчёт по прогону доступен в интерфейсе и как артефакт пайплайна.

## Вне скоупа

- Собственный анализатор кода, свои правила поиска уязвимостей.
- DAST, сканирование запущенных приложений, пентест.
- Runtime-защита, WAF, мониторинг продакшена.
- Безопасность мобильных приложений.
- Автоматическое исправление находок и генерация pull request с фиксом.
- Мультитенантность, биллинг, тарифы.
- SSO, LDAP, интеграция с корпоративным каталогом.
- ML-триаж и автоматическая оценка ложных срабатываний.

## Отложено (следующие версии)

- **Второй CI (GitHub Actions)** — сначала один сценарий до конца, второй после стабилизации.
- **DAST-проверки** — другой класс инструментов и другая модель находок, расширяет V1 в разы.
- **Уведомления в мессенджер и почту** — не влияет на основной сценарий, добавляется после.
- **Экспорт метрик в Prometheus/Grafana** — для диплома достаточно собственного дашборда, внешняя наблюдаемость позже.
- **Правила на основе политик организации (OPA)** — движок политик сложнее, чем нужно V1.

## Сценарии

### S-001 Основной успех: проверка проходит

- Актор: разработчик.
- Предусловия: проект подключён, политика настроена, baseline зафиксирован.
- Поток:
  1. Разработчик создаёт merge request.
  2. CI запускает проверку проекта для коммита.
  3. Система выполняет SAST, проверку секретов и зависимостей.
  4. Результаты приводятся к единой модели и сравниваются с baseline.
  5. Политика выносит вердикт `pass`.
  6. Формируется отчёт, пайплайн продолжается.
- Результат: разработчик видит вердикт и отчёт, релиз не задержан.

### S-002 Блокировка: найдена новая критическая уязвимость

- Актор: разработчик.
- Предусловия: политика блокирует `critical` и `high`, находки нет в baseline.
- Поток:
  1. CI запускает проверку.
  2. Сканер находит уязвимость уровня `critical`.
  3. Система помечает находку как новую.
  4. Политика выносит вердикт `fail`.
  5. Пайплайн завершается с ненулевым кодом, отчёт приложен артефактом.
- Результат: мерж заблокирован, разработчик видит правило, файл и строку.

### S-003 Legacy-проект: baseline не даёт заблокировать всё

- Актор: тимлид.
- Предусловия: в проекте 300 исторических находок.
- Поток:
  1. Тимлид фиксирует текущее состояние как baseline.
  2. Разработчик вносит изменение без новых нарушений.
  3. Система находит те же 300 находок и помечает их как существующие.
  4. Вердикт `pass`.
- Результат: проект можно подключить, не останавливая разработку.

### S-004 Сканер недоступен или превысил таймаут

- Актор: система.
- Предусловия: политика разрешает fail-open для деградировавших проверок.
- Поток:
  1. Один из сканеров падает или не укладывается в таймаут.
  2. Система помечает проверку как `degraded`, фиксирует причину.
  3. Вердикт формируется по оставшимся проверкам, пайплайн не блокируется.
  4. В отчёте явно указано, что покрытие неполное.
- Результат: инфраструктурный сбой не останавливает релиз, но виден в отчёте.

### S-005 Ложное срабатывание: исключение с ограниченным сроком

- Актор: разработчик.
- Предусловия: находка признана ложной.
- Поток:
  1. Разработчик создаёт исключение: правило, путь, причина, срок действия.
  2. Система перестаёт учитывать находку в вердикте до истечения срока.
  3. По истечении срока находка снова влияет на вердикт.
  4. Все действия попадают в журнал аудита.
- Результат: шум убран, но не навсегда и с историей.

### S-006 Дашборд: динамика по проекту

- Актор: тимлид.
- Предусловия: по проекту выполнено не менее двух прогонов.
- Поток:
  1. Тимлид открывает страницу проекта.
  2. Система показывает последние прогоны, тренд находок по severity, топ срабатывающих правил.
- Результат: видно, становится лучше или хуже, без выгрузок вручную.

## Решения по открытым вопросам

- **CI:** GitHub Actions — основной и приёмочный, GitLab CI — второй, поддержка обоих обязательна (FR-019, FR-021).
- **Интерфейс:** простой серверный веб-интерфейс входит в MVP (FR-010).
- **Экономика:** только демо-стенд, расчёт на явных допущениях.

Открытых вопросов нет.
