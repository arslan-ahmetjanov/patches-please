# Delta-спека 002: токены проектов

Статус: принята 21.11.2026. Дополняет [spec.md](spec.md), не заменяя её.
Основание — задача T-006.

## Зачем

FR-009 описывает REST API для запуска прогона, статуса, находок и политики.
Жизненного цикла токена проекта там нет: в плане токен упомянут как средство
доступа из CI, но ни выдачи, ни отзыва, ни одноразового показа спека не
требует. T-006 опиралась на FR-009 по ошибке: тесты `tests/test_tokens.py`
числились покрытием API прогонов, которого не касаются.

Эта delta-спека вводит отдельные требования на выдачу и отзыв токена. FR-009
остаётся за T-007 и T-008 и не меняется.

## Требования

| ID | Требование (EARS) | Приоритет | Критерий приёмки (Дано — Когда — Тогда) |
| --- | --- | --- | --- |
| FR-024 | Когда владелец проекта создаёт токен, система ДОЛЖНА сохранить только его хеш и показать открытое значение ровно один раз — в ответе на создание. | must | Дано пользователь вошёл и он `owner` проекта; Когда отправлен `POST /api/v1/projects/{project_id}/tokens` с названием; Тогда ответ 201 `{id, name, token, created_at}`, в `project_tokens` лежит SHA-256 токена в hex, а повторный `GET` списка открытого значения не содержит. Без сессии — 401, не участник — 404, `member` — 403, пустое или длиннее 100 символов название — 422 без присланных значений. |
| FR-025 | Когда владелец отзывает токен, система ДОЛЖНА пометить его недействительным, не удаляя историю. | must | Дано токен создан; Когда вызван `DELETE /api/v1/projects/{project_id}/tokens/{token_id}`; Тогда ответ 204, у строки заполнен `revoked_at`, проверка этого токена даёт «недействителен», повторный отзыв тоже 204. Токен другого или несуществующего проекта — 404, `member` — 403. |

## Решения и детали

- **Формат токена.** `sg_` + `secrets.token_urlsafe(32)`: 32 байта энтропии,
  46 символов. Префикс отличает токен Security Gate от прочих строк, если он
  попадёт в лог сканера. В `project_tokens` хранится только SHA-256 в hex
  (64 символа, уникальный) — та же функция `token_hash`, что у cookie-сессии:
  значение высокоэнтропийное, соль и медленный хеш не дают выигрыша, а
  проверка идёт на каждом запросе CI.
- **Одноразовый показ.** Открытое значение собирается в `create_token` и
  возвращается вызывающему; модель его не содержит. Список отдаёт только
  метаданные, поэтому после ответа 201 значение восстановить нельзя.
- **Права.** До T-025 проверка живёт в `app/tokens/router.py` и опирается на
  `project_members`: создаёт и отзывает `owner`, `member` видит список без
  открытых значения, посторонний или несуществующий проект — 404, чтобы не
  раскрывать наличие чужого проекта. `member` на запись получает 403: проект
  ему известен, скрывать нечего. T-025 перенесёт проверку в
  `app/auth/permissions.py`.
- **Идентификатор проекта.** В пути — UUID, как в таблице REST API плана.
  Slug остаётся для страниц. Неверный UUID отсекается валидацией (422).
- **Отзыв мягкий.** `revoked_at` заполняется, строка остаётся: история токенов
  и будущий аудит (T-015) не теряются. `verify_token` отозванный токен не
  находит, а `last_used_at` обновляет при успешной проверке.
- **Список.** Без него «повторно не отдаётся» не проверить снаружи, поэтому
  `GET` входит в T-006. Порядок — от новых к старым, при равенстве — по имени.

## Ограничения

- Проверки Bearer-токена в запросах прогона нет: это T-008. `securitySchemes`
  в контракт не добавляются: это T-007, иначе контракт разойдётся с живым
  `/openapi.json`.
- Страницы управления токенами нет: форма выйдет со страницей проекта (T-022)
  или настроек (T-024). HTML-маршруты в REST-контракт не входят.
- Журнала аудита действий с токенами нет: он появится вместе с `audit_events`
  в T-015.
- Токенов на пользователя не ограничиваем: лимитов в V1 нет.
