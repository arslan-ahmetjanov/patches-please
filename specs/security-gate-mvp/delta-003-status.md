# Delta-спека 003: жизненный цикл прогона

Статус: принята 22.11.2026. Дополняет [spec.md](spec.md), не заменяя её.
Основание — задача T-009.

## Зачем

T-009 в `tasks.md` ссылалась на FR-016, но FR-016 — про классификацию находок
(`new`/`existing`/`fixed`), а не про статусы прогона. Требования на смену статуса
в `spec.md` нет: план описывает поток «`queued` → `running` → `done`» и перевод
зависшего прогона в `error` по таймауту, но не фиксирует допустимые переходы,
повторные вызовы и момент заполнения `started_at`/`finished_at`.

Эта delta-спека вводит отдельное требование на жизненный цикл прогона. FR-016
остаётся за T-014 и не меняется.

## Требования

| ID | Требование (EARS) | Приоритет | Критерий приёмки (Дано — Когда — Тогда) |
| --- | --- | --- | --- |
| FR-026 | Когда прогон меняет статус, система ДОЛЖНА допускать только переходы `queued → running`, `running → done` и `queued`/`running` → `error`, заполняя время начала, время завершения и причину ошибки. | must | Дано прогон в статусе `queued`; Когда воркер берёт задачу; Тогда статус `running`, `started_at` заполнен, `finished_at` и `error` пусты. Дано `running`; Когда обработка завершена успешно; Тогда статус `done` и `finished_at`, а при сбое — `error`, `finished_at` и непустая причина в `error`. Недопустимые переходы (`queued → done`, `done → running`, повторный `running → running`, любой переход из `error`) отклоняются доменным исключением, строка прогона не меняется. Заполненное время повторно не перезаписывается. |

## Решения и детали

- **Статусы в БД — строки.** Колонка `scans.status` уже есть с `queued` по
  умолчанию; перечисление `ScanStatus` живёт в `app/scans/service.py` и
  проверяет значение при каждом переходе. Ограничение `CHECK` в схеме не
  добавляем: набор статусов ещё может расшириться, а миграция ради перечисления
  усложнила бы откат.
- **Матрица переходов.** `queued → running`, `queued → error`,
  `running → done`, `running → error`. `done` и `error` терминальны: после них
  прогон не меняется. Повтор `running → running` тоже отклоняется — иначе
  повторная доставка задачи перезаписала бы `started_at`.
- **Время.** `started_at` ставится при переходе в `running`, `finished_at` — при
  `done` и `error`. Оба заполняются только если ещё пусты: повторный вызов
  завершения не переписывает время первого события.
- **Причина ошибки.** Для `error` причина обязательна: пустая строка после
  `strip()` отклоняется. Текст обрезается по краям; для остальных статусов
  причина не принимается.
- **Форма отказа.** Наружу статус только читается, эндпоинта смены статуса нет,
  поэтому доменного исключения `ScanTransitionError` достаточно. HTTP-код для
  конфликта появится вместе с операцией, которой он нужен.
- **Границы T-009.** Задача воркера переводит прогон `queued → running` — это
  и есть «прогон начат» по FR-001. `done` и `error` выставляет обработка
  прогона: сканеры, нормализация и политика (T-010…T-019). Обработчик не падает
  на чужом статусе: повторная задача пишет предупреждение и оставляет прогон.
- **Транзакции.** Смена статуса коммитится вместе с полями времени, по образцу
  `app/tokens/service.py`: вызывающий код не думает о границах транзакции.
  Позже сюда же попадёт запись находок — план требует обновлять статус и
  результаты одной транзакцией.

## Ограничения

- Лимита «один активный прогон на проект» нет: частичный уникальный индекс по
  `project_id` для `queued`/`running` — изменение схемы БД и отдельная задача.
  Гонка двух одновременных `POST` с тем же коммитом остаётся.
- Таймаута зависшего прогона нет: перевод в `error` по времени — T-010.
- Смены статуса через API нет: операции `POST /api/v1/scans` и
  `GET /api/v1/scans/{scan_id}` не меняются.
- Автоматического перевода в `done` после сканеров нет: это T-011…T-020.
