# Delta-спека 001: аутентификация интерфейса

Статус: принята 21.11.2026. Дополняет [spec.md](spec.md), не заменяя её.
Основание: задача T-004.

## Зачем

FR-009 в исходной спеке описывает REST API для запуска прогона, статуса, находок
и политики. Входа в интерфейс там нет: T-004 опиралась на FR-009 по ошибке, и
тесты `tests/test_auth.py` числились покрытием API прогонов, которого не касаются.
Эта delta-спека вводит отдельные требования на вход и выход. FR-009 остаётся
за T-006, T-007 и T-008 и не меняется.

## Требования

| ID | Требование (EARS) | Приоритет | Критерий приёмки (Дано, Когда, Тогда) |
| --- | --- | --- | --- |
| FR-022 | Когда пользователь передаёт email и пароль, система ДОЛЖНА при верных данных открыть сессию и вернуть данные пользователя, а при неверных отказать, не раскрывая наличие учётной записи. | must | Дано есть учётная запись; Когда передан верный пароль; Тогда ответ 200, в ответе `id`, `email`, `role`, в Set-Cookie токен сессии, в `sessions` только SHA-256 токена. Когда пароль неверен или email неизвестен; Тогда ответ 401 с одинаковым телом, кодом и без различимой по времени разницы. Пароль хранится только scrypt-хешем. |
| FR-023 | Когда пользователь выходит, система ДОЛЖНА закрыть его сессию и очистить cookie. | must | Дано пользователь вошёл; Когда вызван выход; Тогда ответ 204 (API) или 303 на `/login` (форма), строки `sessions` с этим токеном больше нет, cookie очищена. Повторный выход без сессии тоже успешен. |

## Решения и детали

- **Два входа, один сервис.** REST (`POST /api/v1/auth/login`, `POST /api/v1/auth/logout`)
  и HTML-форма (`GET/POST /login`, `POST /logout`) вызывают одни и те же функции
  `patches_please/auth/service.py`. HTML-маршруты в REST-контракт не входят.
- **Пароль.** `hashlib.scrypt`, n=2¹⁴, r=8, p=1, dklen=32, соль 16 байт. Формат
  строки: `scrypt$n$r$p$соль_hex$хеш_hex`, параметры читаются из неё. Сверку делает
  `hmac.compare_digest`; битый формат даёт `False`, а не исключение.
- **Неразличимость отказа.** Неверный пароль и неизвестный email дают один ответ:
  401 «Неверный email или пароль». Для неизвестного email scrypt всё равно
  считается по фиктивному хешу, чтобы наличие учётной записи нельзя было определить
  по времени ответа.
- **Сессия.** Токеном служит `secrets.token_urlsafe(32)`, в БД лежит только SHA-256 в hex.
  Срок 7 дней, `expires_at` в UTC. Cookie `pp_session`: HttpOnly,
  SameSite=Lax, Path=/, без Domain. Протухшая строка удаляется при обращении.
- **Ответы валидации.** Тело 422 не содержит присланных значений (`input` и `ctx`):
  иначе пароль попадал бы в ответ и в логи. Контракт описывает только `type`,
  `loc`, `msg`.

## Ограничения

- Флаг `secure` у cookie выключен, потому что локальный стенд работает по HTTP. Для HTTPS флаг
  включается вместе с CSRF в T-024; это зафиксировано в описании задачи.
- CSRF-токенов в T-004 нет: защита ограничена SameSite=Lax, полноценная защита приходит в T-024.
- Регистрации нет. Учётные записи создаёт сервисная функция `create_user`; первого
  реального пользователя заводит демо-сев (T-032).
- Неверный email не нормализуется (регистр, пробелы): сопоставление точное.
