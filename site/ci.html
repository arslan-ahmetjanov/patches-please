CI

Проверка встраивается в пайплайн двумя способами: готовое композитное действие для GitHub Actions и шаблон job для GitLab CI. Оба ставят один CLI patches-please, ждут вердикт и возвращают его кодом выхода.

GitHub Actions

Настройка репозитория состоит из трёх шагов.

  1. Создайте токен проекта. Он выдаётся один раз в ответе POST /api/v1/projects/{project_id}/tokens, создавать может владелец проекта. Значение имеет вид pp_... и больше не показывается.

  2. Положите токен в секрет репозитория PATCHES_PLEASE_TOKEN: Settings, Secrets and variables, Actions, Secrets.

  3. Положите адрес сервиса в переменную репозитория PATCHES_PLEASE_URL, там же в разделе Variables. Укажите полный http(s)-адрес без /api/v1, например https://patches.example.ru.

Workflow целиком:

name: Проверка безопасности

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  scan:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7

      - uses: ./.github/actions/patches-please
        with:
          server: ${{ vars.PATCHES_PLEASE_URL }}
          token: ${{ secrets.PATCHES_PLEASE_TOKEN }}

На pull_request значение github.sha по умолчанию указывает на коммит слияния, а не на коммит ветки. Если проверять нужно сам коммит из PR, передайте его явно: 

      - uses: ./.github/actions/patches-please
        with:
          server: ${{ vars.PATCHES_PLEASE_URL }}
          token: ${{ secrets.PATCHES_PLEASE_TOKEN }}
          commit: ${{ github.event.pull_request.head.sha }}

Из другого репозитория действие вызывается по пути внутри репозитория. Для воспроизводимости закрепите ссылку коммитом или тегом вместо main. 

      - uses: arslan-ahmetjanov/patches-please/.github/actions/patches-please@main
        with:
          server: ${{ vars.PATCHES_PLEASE_URL }}
          token: ${{ secrets.PATCHES_PLEASE_TOKEN }}

Входы действия

Входы композитного действия patches-please
Вход Обязателен По умолчанию Назначение
server да нет Адрес API сервиса, http(s)://host[:port]
token да нет Токен проекта pp_...; передавайте из secrets
provider нет github Провайдер: github или gitlab
commit нет github.sha Полный SHA проверяемого коммита
ref нет github.ref git ref: main, refs/heads/main
timeout нет 900 Общий дедлайн команды в секундах

Выходов у действия нет: результат читается по коду выхода шага и по логу клиента. Токен маскируется до того, как попадёт в окружение клиента, поэтому в логах его нет при любом коде выхода.

GitLab CI

Шаблон лежит в ci/gitlab/patches-please.yml и подключается через include и extends. Адрес сервиса и токен берутся из CI/CD-переменных, в файле их значений нет. 

include:
  - local: ci/gitlab/patches-please.yml

stages:
  - test

patches-please:
  extends: .patches-please
  stage: test
  when: manual
  allow_failure: true

Переменные задаются в Settings, CI/CD, Variables:

  • PATCHES_PLEASE_URL: адрес сервиса, например https://patches.example.ru;
  • PATCHES_PLEASE_TOKEN: токен проекта вида pp_..., пометьте masked и protected;
  • PATCHES_PLEASE_CLI_TOKEN: токен на чтение, нужен только если репозиторий клиента приватный, пометьте masked и protected.

when: manual оставляет запуск ручным: пока сервис не развёрнут, прогон не пройдёт, а пайплайн на каждый push падать не должен. allow_failure: true держит пайплайн зелёным: job получает код клиента и краснеет при fail, но пайплайн остаётся успешным. Уберите обе настройки, когда проверка должна блокировать слияние.

Коды выхода

Коды возврата клиента в CI
Код Значение
0 Вердикт pass (или прогон только запущен без --wait)
1 Вердикт fail
2 Ошибка аргументов или адреса: нет провайдера, коммита, ref или токена; неверные --server, --timeout, --interval; 3xx; 404 на старте; 4xx от API
3 401, 403 или 404 при опросе: нет доступа к прогону
4 status=error, завершение без вердикта или неполный ответ сервиса
5 Истёк --timeout в ожидании
6 Сеть, 5xx после повторов или непредвиденная ошибка клиента

Что важно помнить

  • Job падает при любом ненулевом коде. 1 (находки блокирующего уровня) и 2…6 (сбой проверки) в интерфейсе выглядят одинаково; различить их можно по коду в логе шага и по сообщению клиента в stderr.
  • Раннер не видит localhost. Сервису нужен публичный адрес: развёрнутый стенд или временный туннель к локальному. Порядок развёртывания описан на странице «Сервер».
  • Опись меняет картину. Исторические находки из описи получают состояние existing и не блокируют прогон, новые находки блокируют. Порядок установки описи: «Первый прогон».
  • Повторный запуск. Повторный POST того же коммита возвращает существующий прогон при любом статусе, включая error: перезапуск job не создаст новый прогон.
  • Без --wait гейта нет. Клиент только создаёт прогон и выходит с кодом 0. Если повторный POST вернул уже завершённый прогон, вердикт применяется и без флага.
