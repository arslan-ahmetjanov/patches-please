Вопросы

Короткие ответы на то, что спрашивают чаще всего: место системы среди готовых сервисов, поведение при сбоях, доступ к репозиториям, хранение данных и лицензии.

Чем это отличается от Dependabot и Snyk

Dependabot работает внутри GitHub и следит за зависимостями: находит известные уязвимости в манифестах и открывает pull request с обновлением версий. Snyk это отдельная платформа проверок: код, зависимости, образы контейнеров, свой набор интеграций и отчётов.

Patches, Please решает другую задачу: один прогон коммита объединяет три класса проверок (SAST, секреты, уязвимые зависимости), приводит находки к одной модели и выносит вердикт по политике проекта. Наружу уходит не список предупреждений, а код выхода: 0 при pass, 1 при fail.

Отсюда практические различия. Система разворачивается на своей машине, сканеры работают офлайн, а вердикт считается на вашем сервере по вашим порогам, описи и разрешениям. Инструмент не обновляет зависимости и не предлагает исправлений: он пропускает или задерживает патч.

Чем от GitHub Advanced Security

GitHub Advanced Security это набор возможностей внутри GitHub: сканирование кода, поиск секретов и обзор зависимостей, с алертами в интерфейсе GitHub. Patches, Please работает с GitHub и GitLab одинаково: для него провайдер это поле в истории прогона, а не платформа.

Результаты остаются у вас: прогоны, находки и отчёты лежат в вашей PostgreSQL и на томе reportsdata, алерты code scanning в GitHub не появляются. Обратная сторона: готовых интеграций с очередью задач и правилами защиты веток GitHub у системы нет, только шаг пайплайна с кодом выхода.

Что будет, если сканер упал

Проверка получает статус degraded, причина записывается в прогон. В интерфейсе такой прогон помечен как «досмотр неполный». Причиной бывает и сбой инструмента, и таймаут: общий таймаут сканеров задаётся в политике проекта и по умолчанию равен 300 с.

Дальше работает режим деградации из политики. При fail-open отказ сканера не блокирует релиз, при fail-closed прогон получает fail. Режим выбирается в настройках проекта, вместе с блокирующими уровнями важности.

Как проверить приватный репозиторий

В текущей версии никак: worker клонирует репозиторий по адресу repo_url без учётных данных. Приватный адрес даёт прогон со статусом error, в причине будет клонирование.

Это ограничение, а не настройка. Для проверки указывайте публичный HTTPS-адрес. Локальный путь и смонтированный каталог тоже не подходят: контейнер получает только URL.

Можно ли работать вдвоём

Да. В проекте две роли членства: owner и member. Видимость определяется членством: пользователь видит только проекты, где он участник. Создатель проекта сразу получает owner; менять политику и разрешения может только владелец.

Регистрации нет: учётные записи создаёт сервисная функция create_user или сев scripts/seed_demo.py. Отдельной страницы управления участниками в интерфейсе нет, состав проекта задаётся в базе.

Где лежат отчёты и как их забрать

После прогона worker пишет два файла в каталог REPORTS_DIR (по умолчанию /app/reports): <scan_id>.json и <scan_id>.html. Каталог смонтирован из тома reportsdata.

Метода API для скачивания нет: файлы забирают с тома средствами Docker. HTML самодостаточен, стили встроены, поэтому открывается локально без сервера. Тот же прогон целиком виден на странице прогона в интерфейсе.

Как обновляется база уязвимостей Trivy

База зашита в образ worker при сборке, в работе используется флаг --skip-db-update: сканер не ходит в сеть. Между пересборками база не меняется, свежесть определяет пересборка.

Порядок обновления: изменить в Dockerfile.worker аргумент TRIVY_DB_REVISION и собрать образ заново, тогда сбросится кеш только слоя с базой. Дата базы проверяется в контейнере: 

docker run --rm patches-please-worker:local cat /opt/trivy-cache/db/metadata.json

После обновления число находок может измениться: база новее, находок больше. На демо-наборе это видно сразу, поэтому опись и число находок в отчётах придётся обновить.

Что с секретами

Находки-секреты маскируются при нормализации: в базу и в оба отчёта попадает заглушка [секрет скрыт], правило, путь и строка остаются. Gitleaks дополнительно маскирует секрет в своём SARIF флагом --redact. Вывод сканеров в лог не пишется.

Пароль пользователя хранится только хешем scrypt (n=2¹⁴, r=8, p=1, соль 16 байт). Токен проекта показывается один раз, в базе лежит его SHA-256. Неверный пароль и неизвестный email дают одинаковый ответ 401.

Сессия живёт в cookie pp_session: HttpOnly, SameSite=Lax, Path=/, срок 7 дней. Флаг Secure включается при APP_ENV, отличном от local. В примерах и документации пароли и токены только заглушками.

Почему название такое

Отсылка к игре Papers, Please: инспектор на границе пропускает или задерживает документы, а система пропускает или задерживает патч. Кто играл, тот услышит; кто не играл, прочитает буквально.

Метафора продолжается в словаре интерфейса: прогон называется досмотром, находка нарушением, baseline описью, исключение разрешением со сроком. В API и в документации остаются scan, pass, fail, finding, baseline, exception.

Можно ли развернуть в кластере

Нет. Развёртывание рассчитано на Docker Compose на одной машине: четыре сервиса, локальные тома, без кластера, балансировки и внешней PostgreSQL. Инструкция такие конфигурации не покрывает.

Ограничение осознанное: кластер, балансировка и внешняя PostgreSQL в объём системы не входят. Для стенда и небольшой команды хватает одной машины с четырьмя сервисами Compose.

Под какой лицензией проект и сканеры

Код и документация Patches, Please распространяются по лицензии MIT. Сканеры сохраняют свои лицензии:

Лицензии сканеров и инфраструктуры
Компонент Версия Лицензия
Semgrep 1.186.0 LGPL-2.1
Gitleaks 8.30.1 MIT
Trivy 0.76.2 Apache-2.0
PostgreSQL 16 PostgreSQL License
Redis 7.2 BSD-3-Clause

Semgrep под LGPL-2.1 запускается отдельным процессом и не модифицируется, поэтому его копилефт не распространяется на код проекта. Redis закреплён на ветке 7.2: начиная с 7.4 он выходит под RSALv2 и SSPLv1, которые не одобрены OSI.
