Неполадки

Большая часть сбоев видна по состоянию контейнеров и ответу /health. Начните с короткого порядка разбора, затем найдите свой симптом в таблице.

Порядок разбора

  1. Посмотрите состояние сервисов. Четыре строки Up с пометкой (healthy) означают, что стек поднялся. 
    docker compose ps
  2. Прочитайте логи обоих приложений. У api и worker разные причины отказа. 
    docker compose logs -f --tail=100 api worker
  3. Проверьте healthcheck API. 
    curl http://localhost:8000/health

    Если /health отвечает, а страницы отдают 500, дело в схеме базы, а не в запуске.

  4. Примените миграции и сверьте модели. 
    uv run alembic upgrade head
uv run alembic check

    Ожидаемо: семь строк Running upgrade … с последней 0007 и ответ No new upgrade operations detected.

Три частых случая

Прогон долго в queued

Прогон создан и лежит в очереди, но задачу никто не взял. Очередь держит Redis, забирает задачи worker. Первым делом проверьте его состояние и логи: если контейнер остановлен или у него статус unhealthy, прогон останется в queued, сколько бы вы ни ждали. 

docker compose ps worker
docker compose logs worker

Healthcheck worker проверяет регистрацию обработчика в очереди, поэтому подсказка в выводе обычно прямая. Частая причина рядом: контейнер redis не запущен или адрес в REDIS_URL не совпадает с сервисом Compose.

Прогон error из-за клонирования

Причина со словом «клон» означает, что worker не смог получить репозиторий. Учётных данных для клонирования у него нет, поэтому приватный адрес или опечатка в URL дают статус error.

В проекте должен стоять публичный HTTPS-адрес вида https://github.com/<аккаунт>/<репозиторий>.git. Локальный путь и смонтированный каталог не подходят: контейнер получает только URL. Тот же прогон не создастся повторно, даже с исправленным адресом: повторный запрос с тем же коммитом возвращает существующий прогон, нужен новый коммит.

Вход не сохраняется

Форма принимает пароль, но следующая страница снова просит войти. Значит, браузер не отправил cookie сессии. При APP_ENV, отличном от local, cookie pp_session и CSRF помечаются Secure: по HTTP браузер их не вернёт.

Для стенда по HTTP верните APP_ENV=local и перезапустите сервисы. Для работы по HTTPS оставьте другое значение и поднимите обратный прокси с сертификатом: порядок описан на странице «Сервер».
