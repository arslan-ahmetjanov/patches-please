# Замеры производительности

Фактические результаты замеров с датой, окружением и командой. Цифры не
оценочные: каждая запись получена запуском на стенде, описанном в этой же
записи. Если замер не выполнялся, так и написано.

## NFR-001 — отклик API при 20 RPS (T-029)

Требование: система отвечает на запросы API с p95 не более 300 мс при 20 RPS,
без учёта запуска сканеров.

**Итог: порог пройден, p95 = 24.93 мс.**

### Дата

2026-11-25, локальное время (UTC+05:00).

### Окружение

| Что | Значение |
| --- | --- |
| Машина | HUAWEI RLEF-XX, Windows 11 Pro 10.0.26300 |
| Процессор | Intel Core i5-12500H, 12 ядер / 16 потоков |
| ОЗУ хоста | 16 111 МБ (16 ГБ) |
| Docker | Docker Desktop 29.0.1, ядро WSL2 6.6.87.2 |
| Ресурсы Docker VM | 16 CPU, 9.711 GiB ОЗУ |
| Стенд | `docker compose`: `postgres:16-alpine`, `redis:7.2-alpine`, образы `patches-please-api:local` и `patches-please-worker:local` |
| Нагрузочный инструмент | k6 v2.4.0 (windows/amd64) |

Тег Redis в таблице — текущий, из `docker-compose.yml`. Замер выполнялся до T-031,
когда там стоял `redis:7-alpine`: цифры получены на нём и не пересчитывались.

Замер шёл с хоста в опубликованный порт API. Порт 8000 на этой машине попадает
в зарезервированный Windows диапазон 7979–8078 (`netsh int ipv4 show
excludedportrange protocol=tcp`), поэтому API опубликован на 8081 через
временный override-файл Compose. На стенде без такого ограничения адрес —
`http://localhost:8000`.

### Стенд и данные

Перед замером: `docker compose up -d`, `curl /health` → `{"status":"ok"}`,
`uv run alembic upgrade head`.

Для замера заведены отдельные данные, не связанные с демо и тестами:

- пользователь `load-t029@example.com`;
- проект `load-t029`;
- токен проекта из `patches_please.tokens.service.create_token`;
- прогон с коммитом `dddd…` (40 символов `d`), статусом `done` и вердиктом
  `pass` — так `GET /api/v1/scans/{id}` отвечает 200 без работы воркера.

Данные создавались временным скриптом на хосте поверх `DATABASE_URL` на
`localhost:5432`; в репозиторий он не входит. Открытый токен и `SCAN_ID` в
репозитории не хранятся: k6 получает их переменными окружения.

### Профиль нагрузки

Сценарий `api_20rps` в `tests/load/k6.js`:

| Параметр | Значение |
| --- | --- |
| Исполнитель | `constant-arrival-rate` |
| Интенсивность | 20 итераций/с (NFR-001) |
| Длительность | 60 с |
| Итераций | 1201 |
| VU | 20 предвыделенных, до 100 при просадке |
| Запросов в итерации | 1 |
| Смесь эндпоинтов | чётные итерации — `GET /api/v1/scans/{id}`, нечётные — `GET /health` (около 50/50) |
| Порог | `http_req_duration: p(95)<300`, `http_req_failed: rate<0.01` |

`POST /api/v1/scans` в цикл не включён: он пишет строку в БД, ставит задачу в
Redis и дедуплицирует прогоны по коммиту, то есть меняет состояние. Сканеры не
запускались: воркер во время замера простаивал, прогон уже был в статусе `done`.
`GET /api/v1/scans/{id}` — это реальный путь CI: обёртка поллит его до вердикта,
и проверка токена в нём включает запись `last_used_at`.

`setup()` проверяет окружение до старта: `TOKEN` и `SCAN_ID` заданы, `/health`
отвечает 200, прогон доступен по токену. Без этого профиль молча измерил бы
только healthcheck.

### Команда

```bash
k6 run \
  -e BASE_URL=http://localhost:8081 \
  -e TOKEN=pp_... \
  -e SCAN_ID=<uuid прогона> \
  tests/load/k6.js
```

`BASE_URL` по умолчанию `http://localhost:8000`, `DURATION` — `60s`;
`TOKEN` и `SCAN_ID` обязательны.

### Вывод

NFR-001 выполнен с запасом: p95 24.93 мс против порога 300 мс (около 12 раз).
При 20 RPS API не деградирует, ошибок нет, все проверки прошли.

### Ограничения

- Замер на локальной машине разработчика, а не на демо-стенде 4 vCPU из
  NFR-002. Абсолютные числа зависят от конфигурации; вывод — «порог выполнен
  на описанном стенде», а не «гарантирован на любом железе».
- Один прогон 60 с. Три повтора и максимум из них — требование NFR-002 к
  прогону сканирования (T-030), не к отклику API.
- `POST /api/v1/scans` и запуск сканеров не мерились: см. профиль выше.
- Порт 8081 — следствие ограничения Windows на этой машине, а не часть стенда.

## NFR-002 — полный прогон репозитория до 10 минут (T-030)

Требование: прогон проверки репозитория до 100 тыс. строк должен завершаться
не дольше 10 минут на 4 vCPU. Замер — три прогона, берётся максимум.

**Итог: порог пройден, максимум 12.19 с при пороге 600 с.**

### Дата

2026-11-25, локальное время (UTC+05:00); прогоны шли с 22:09 до 22:10 UTC.

### Окружение

| Что | Значение |
| --- | --- |
| Машина | HUAWEI RLEF-XX, Windows 11 Pro 10.0.26300 |
| Процессор | Intel Core i5-12500H, 12 ядер / 16 потоков |
| ОЗУ хоста | 16 111 МБ (16 ГБ) |
| Docker | Docker Desktop 29.0.1, ядро WSL2 6.6.87.2 |
| Ресурсы Docker VM | 16 CPU, 9.711 GiB ОЗУ |
| Ограничение worker | `cpus: 4.0` (`NanoCpus=4000000000`), остальные сервисы без лимита |
| Стенд | `docker compose`: `postgres:16-alpine`, `redis:7.2-alpine`, образы `patches-please-api:local` и `patches-please-worker:local` |
| Сканеры в образе worker | Semgrep 1.186.0, Gitleaks 8.30.1, Trivy 0.76.2 (база от 2026-11-23) |

Тег Redis в таблице — текущий, из `docker-compose.yml`. Замер выполнялся до T-031,
когда там стоял `redis:7-alpine`: цифры получены на нём и не пересчитывались.

NFR-002 говорит о 4 vCPU. Чтобы приблизить стенд к требованию, worker ограничен
четырьмя CPU временным override-файлом Compose (`cpus: 4.0`); API, PostgreSQL и
Redis не ограничивались. Ограничение проверено через `docker inspect`:
`NanoCpus=4000000000`.

Порт 8000 на этой машине попадает в зарезервированный Windows диапазон
7979–8078, поэтому API опубликован на 8081 тем же временным override. На стенде
без такого ограничения адрес — `http://localhost:8000`.

Перед замером: `docker compose up -d`, `curl /health` → `{"status":"ok"}`,
`uv run alembic upgrade head`. Docker Desktop на этой машине останавливал движок
при простое; все три зачётных прогона прошли подряд на одном поднятом стенде,
без перезапусков worker между ними.

### Репозиторий и объём

| Что | Значение |
| --- | --- |
| Репозиторий | `https://github.com/Textualize/rich` (публичный, Python) |
| Коммит | `3a109ccdffe5b2d0e30684a304fbd388e99ce57b` (полный SHA, ветка `main`) |
| Строк | 73 081 |
| Файлов | 553 отслеживаемых, из них 531 текстовый и 22 двоичных |

Число строк получено на отдельном клоне: `git ls-files` перечисляет
отслеживаемые файлы, для каждого текстового считается число переводов строки;
файлы с нулевым байтом считаются двоичными и не входят в сумму. Пустые строки
входят. Данных работодателя в репозитории нет, это публичный проект.

Репозиторий меньше верхней границы требования (73 % от 100 тыс. строк);
см. «Ограничения».

### Стенд и данные

Для замера заведены отдельные данные, не связанные с демо и тестами:

- пользователь `measure-t030@example.com`;
- проекты `measure-t030-5`, `measure-t030-6`, `measure-t030-7` — по одному на
  повтор, потому что API дедуплицирует прогоны по паре «проект + коммит»;
- у каждого проекта свой токен из `patches_please.tokens.service.create_token`;
- пробный прогон на проекте `measure-t030-1` и первая серия на проектах
  `measure-t030-2`…`measure-t030-4` в результат не входят: они проверяли стенд
  и вывод скрипта.

Данные создавались временным скриптом на хосте поверх `DATABASE_URL` на
`localhost:5432`; в репозиторий он не входит. Открытые токены в репозитории не
хранятся: скрипт замера получает их переменными окружения и не печатает.

### Профиль прогона

Замер идёт через API, как это делает CI:

1. `POST /api/v1/scans` с полным `commit_sha`, `ref` и `provider` — прогон
   создаётся в статусе `queued`, задача уходит в Redis;
2. worker переводит прогон в `running` и выполняет конвейер: клон закреплённого
   коммита (`git fetch --depth 1`), три сканера параллельно, нормализация SARIF,
   классификация по базе сравнения, запись находок, метрики, вердикт `pass`/`fail`
   и два файла отчёта — JSON и HTML;
3. `GET /api/v1/scans/{id}` опрашивается каждые 2 с до `done` или `error`.

В замер входит всё перечисленное, включая клон по сети и запись отчётов. Общий
таймаут сканеров — 300 с из политики проекта (значение по умолчанию), предел
задачи RQ — 600 с (`SCAN_JOB_TIMEOUT_SEC`), то есть ровно порог NFR-002.

Время в таблице ниже — от отправки `POST` до момента, когда поллинг увидел
терминальный статус. Оно включает ожидание в очереди и до одного интервала
опроса, поэтому не меньше времени самого worker; для сверки приведены оба.

### Команда

```bash
MEASURE_API_URL=http://localhost:8081 \
MEASURE_TOKENS="measure-t030-5=pp_...,measure-t030-6=pp_...,measure-t030-7=pp_..." \
MEASURE_COMMIT_SHA=3a109ccdffe5b2d0e30684a304fbd388e99ce57b \
MEASURE_REF=main \
uv run python scripts/measure_scan.py
```

Умолчания скрипта: `MEASURE_REPEATS=3`, `MEASURE_LIMIT_SEC=600`,
`MEASURE_TIMEOUT_SEC=900`, `MEASURE_POLL_SEC=2`, `MEASURE_PROVIDER=github`.
Проект задаётся токеном: отдельного поля проекта в API нет, поэтому в
`MEASURE_TOKENS` перед токеном стоит метка проекта.

### Вывод

NFR-002 выполнен с большим запасом: максимум 12.19 с против порога 600 с
(около 49 раз). Даже на четырёх CPU полный прогон репозитория на 73 тыс. строк
с клоном, тремя сканерами, отчётами и вердиктом занимает секунды, а не минуты.
Предел задачи RQ в 600 с не приближается.

### Ограничения

- Репозиторий — 73 081 строка, это 73 % верхней границы требования. Замер
  доказывает выполнение порога на этом объёме, но не проверяет ровно 100 тыс.
  строк: на границе время будет больше.
- 4 vCPU — ограничение только worker, заданное override-файлом. Хост и Docker
  VM имеют 16 CPU, поэтому фоновая нагрузка и сеть на хосте не ограничены
  четырьмя ядрами.
- Клон идёт с GitHub по сети и входит в замер. На медленном канале или при
  недоступности провайдера время вырастет; офлайн-стенд с локальным зеркалом
  даст другие числа.
- Набор правил Semgrep — локальный, из трёх правил (`scanner-rules/semgrep`),
  как и задумано для офлайн-прогона (NFR-003). С полным реестром правил SAST
  будет медленнее; это ограничение профиля проверки, а не стенда.
- Время по API включает ожидание в очереди и до 2 с опроса, поэтому оно больше
  времени worker. Для сравнения приведены обе величины.
- Замер на локальной машине разработчика, а не на отдельном демо-стенде.
  Абсолютные числа зависят от оборудования; вывод — «порог выполнен на
  описанном стенде», а не «гарантирован на любом железе».
- Данные замеров после хронометража T-033 удалены вместе с томами `pgdata` и
  `reportsdata`: записей о прогонах `measure-t030-*` в БД стенда и файлов отчётов
  нет. Замер воспроизводится скриптом `scripts/measure_scan.py` на поднятом
  стенде.
