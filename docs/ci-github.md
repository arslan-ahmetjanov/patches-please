# CI на GitHub Actions

Инструкция по готовому workflow появится в T-026. Этот файл описывает общую
часть — CLI-клиент `patches-please`, которым пользуются и GitHub Actions,
и GitLab CI. Один клиент — один протокол: обёртки провайдеров только ставят
пакет и вызывают `patches-please scan`.

## Установка

Из репозитория:

```bash
uv sync
```

Из wheel, собранного `uv build`:

```bash
pip install dist/patches_please-0.1.0-py3-none-any.whl
```

Клиенту нужен только Python 3.12 и пакет `patches_please`; база, Redis и файлы
репозитория не требуются (NFR-007).

## Запуск

```bash
export PATCHES_PLEASE_URL="https://patches.example.ru"
export PATCHES_PLEASE_TOKEN="pp_..."

uv run patches-please scan \
  --provider github \
  --commit "$GITHUB_SHA" \
  --ref "$GITHUB_REF" \
  --wait
```

Из активированного окружения или после `pip install` команда вызывается без
`uv run`. `--provider` обязателен: клиент не угадывает провайдера по переменным
раннера. `--commit` — полный SHA, `--ref` — git ref (`main`, `refs/heads/main`).
Флаг важнее переменной окружения: `--server` и `--token` переопределяют
`PATCHES_PLEASE_URL` и `PATCHES_PLEASE_TOKEN`.

Без `--wait` клиент только создаёт прогон и выходит с кодом 0. Для гейта
в CI нужен `--wait`: тогда код выхода определяется вердиктом. Если повторный
`POST` вернул уже завершённый прогон, вердикт применяется и без `--wait`.

## Коды выхода

| Код | Значение |
| --- | --- |
| 0 | вердикт `pass` (или прогон только запущен без `--wait`) |
| 1 | вердикт `fail` |
| 2 | ошибка аргументов или адреса: нет провайдера, коммита, ref или токена; неверные `--server`, `--timeout`, `--interval`; `3xx`; `404` на старте; `4xx` от API (например, `422` на неверный SHA) |
| 3 | `401`, `403` или `404` при опросе: нет доступа к прогону |
| 4 | `status=error`, завершение без вердикта или неполный ответ сервиса |
| 5 | истёк `--timeout` в ожидании |
| 6 | сеть, `5xx` после повторов или непредвиденная ошибка клиента |

`--timeout` (по умолчанию 900 с) — общий дедлайн команды: старт, повторы
и ожидание вместе. Повторяются только `5xx` и сетевые ошибки при опросе
статуса; `4xx` не повторяется. Редиректы не преследуются: клиент просит указать
конечный `https`-адрес в `--server`, код 2.

Пример с машиночитаемым выводом и своим таймаутом:

```bash
uv run patches-please scan \
  --provider github --commit "$GITHUB_SHA" --ref "$GITHUB_REF" \
  --wait --json --timeout 600
```

## Вывод

Человекочитаемый режим печатает прогон, статус, вердикт и две строки —
«Находки по severity» и «Отчёт». Пока этих данных в API нет, в строках стоит
пометка, что они появятся вместе с отчётами (T-020). С `--json` в stdout уходит
ровно один JSON-объект прогона, диагностика — в stderr. Токен не печатается
ни в одном режиме, включая `--verbose` и сообщения об ошибках.

## Ограничения MVP

- Находки по severity и адрес отчёта появятся вместе с отчётами (T-020).
  До этого клиент печатает на их месте явную пометку.
- До T-017 сервис не выставляет `verdict` и не переводит прогон в `done`:
  worker завершает прогоны только ошибкой. Поэтому реальный `--wait` на
  текущем стенде даст 4 или 5; коды 0 и 1 проверены на `MockTransport`
  и заработают, когда появятся вердикт и отчёты.
- Повторный `POST` того же коммита возвращает существующий прогон при любом
  статусе, включая `error`: перезапуск job не создаст новый прогон. Это
  ограничение сервиса (T-009), а не клиента.
- `--fail-on-degraded` принимается, но пока ничего не передаёт: поля в API нет.
  Клиент пишет предупреждение в stderr и не меняет вердикт — его считает
  политика проекта.
- Самоподписанный стенд требует системного доверия к сертификату: флага
  `--insecure` в MVP нет.
