# CI на GitHub Actions

Два способа подключить проверку: готовое композитное действие
`.github/actions/patches-please` (рекомендуется) и прямой вызов CLI
`patches-please`. Оба используют один клиент и один протокол: обёртка только
ставит пакет и вызывает `patches-please scan`, а ожидание, повторы и перевод
вердикта в код выхода делает клиент (FR-019, FR-020, T-036).

## Готовое действие

Действие `.github/actions/patches-please/action.yml` (T-026) ставит CLI из
этого репозитория и выполняет ровно один вызов:

```bash
patches-please scan --provider <provider> --commit <sha> --ref <ref> --wait
```

Собственного опроса статуса в действии нет: `--wait` — единственный механизм
ожидания. Код выхода клиента становится кодом выхода шага, поэтому job падает
при вердикте `fail` и проходит при `pass` (FR-020, FR-033).

### Настройка репозитория

1. Создайте токен проекта. Токен выдаётся один раз в ответе
   `POST /api/v1/projects/{project_id}/tokens` (создавать может владелец
   проекта); значение имеет вид `pp_...` и больше не показывается.
2. Положите токен в секрет репозитория `PATCHES_PLEASE_TOKEN`
   (Settings → Secrets and variables → Actions → Secrets).
3. Положите адрес сервиса в переменную репозитория `PATCHES_PLEASE_URL`
   (там же, раздел Variables), например `https://patches.example.ru`.
   Адрес — полный `http(s)`-URL без `/api/v1`.

### Пример подключения

```yaml
name: Проверка безопасности

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  scan:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7

      - uses: ./.github/actions/patches-please
        with:
          server: ${{ vars.PATCHES_PLEASE_URL }}
          token: ${{ secrets.PATCHES_PLEASE_TOKEN }}
```

На `pull_request` значение `github.sha` по умолчанию — коммит слияния, а не
коммит ветки. Если проверять нужно сам коммит из PR, передайте его явно:
`commit: ${{ github.event.pull_request.head.sha }}`.

Рабочий пример — `.github/workflows/demo-scan.yml`. Он запускается вручную
(`workflow_dispatch`), потому что без развёрнутого сервиса прогон не пройдёт.

Из другого репозитория действие вызывается по пути внутри репозитория:

```yaml
      - uses: arslan-ahmetjanov/patches-please/.github/actions/patches-please@main
        with:
          server: ${{ vars.PATCHES_PLEASE_URL }}
          token: ${{ secrets.PATCHES_PLEASE_TOKEN }}
```

Для воспроизводимости закрепите ссылку коммитом или тегом вместо `main`.
`actions/checkout` в этом случае не обязателен: действие работает со своей
копией репозитория.

### Входы

| Вход | Обязателен | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `server` | да | — | Адрес API сервиса, `http(s)://host[:port]` |
| `token` | да | — | Токен проекта `pp_...`; передавайте из `secrets` |
| `provider` | нет | `github` | Провайдер: `github` или `gitlab` |
| `commit` | нет | `github.sha` | Полный SHA проверяемого коммита |
| `ref` | нет | `github.ref` | git ref: `main`, `refs/heads/main` |
| `timeout` | нет | `900` | Общий дедлайн команды в секундах |

Выходов у действия нет: результат читается по коду выхода шага и по логу
клиента (прогон, статус, вердикт).

### Как это работает

- Токен маскируется (`::add-mask::`) до того, как попадёт в окружение клиента,
  поэтому в логах его нет ни при каких кодах выхода.
- CLI ставится из корня репозитория действия через `uv sync --frozen --no-dev`:
  публикация в PyPI не нужна, версии зависимостей берутся из `uv.lock`, Python —
  из `.python-version` (3.12). `uv` ставится шагом `astral-sh/setup-uv`.
- Шаги используют `bash`, то есть действие рассчитано на Linux-раннеры
  (`ubuntu-latest`). Раннеру нужен доступ в сеть: за пакетами и до сервиса.
- В действии нет `|| true` и нет собственного цикла опроса: код выхода клиента
  не подавляется.

## Установка без действия

Из репозитория:

```bash
uv sync
```

Из wheel, собранного `uv build`:

```bash
pip install dist/patches_please-0.1.0-py3-none-any.whl
```

Клиенту нужен только Python 3.12 и пакет `patches_please`; база, Redis и файлы
репозитория не требуются (NFR-007).

## Запуск

```bash
export PATCHES_PLEASE_URL="https://patches.example.ru"
export PATCHES_PLEASE_TOKEN="pp_..."

uv run patches-please scan \
  --provider github \
  --commit "$GITHUB_SHA" \
  --ref "$GITHUB_REF" \
  --wait
```

Из активированного окружения или после `pip install` команда вызывается без
`uv run`. `--provider` обязателен: клиент не угадывает провайдера по переменным
раннера. `--commit` — полный SHA, `--ref` — git ref (`main`, `refs/heads/main`).
Флаг важнее переменной окружения: `--server` и `--token` переопределяют
`PATCHES_PLEASE_URL` и `PATCHES_PLEASE_TOKEN`.

Без `--wait` клиент только создаёт прогон и выходит с кодом 0. Для гейта
в CI нужен `--wait`: тогда код выхода определяется вердиктом. Если повторный
`POST` вернул уже завершённый прогон, вердикт применяется и без `--wait`.

## Коды выхода

| Код | Значение |
| --- | --- |
| 0 | вердикт `pass` (или прогон только запущен без `--wait`) |
| 1 | вердикт `fail` |
| 2 | ошибка аргументов или адреса: нет провайдера, коммита, ref или токена; неверные `--server`, `--timeout`, `--interval`; `3xx`; `404` на старте; `4xx` от API (например, `422` на неверный SHA) |
| 3 | `401`, `403` или `404` при опросе: нет доступа к прогону |
| 4 | `status=error`, завершение без вердикта или неполный ответ сервиса |
| 5 | истёк `--timeout` в ожидании |
| 6 | сеть, `5xx` после повторов или непредвиденная ошибка клиента |

В GitHub и GitLab job падает при любом ненулевом коде, поэтому `1` (находки
блокирующего уровня) и `2…6` (сбой проверки) в интерфейсе выглядят одинаково.
Различить их можно по коду в логе шага и по сообщению клиента в stderr.

`--timeout` (по умолчанию 900 с) — общий дедлайн команды: старт, повторы
и ожидание вместе. Повторяются только `5xx` и сетевые ошибки при опросе
статуса; `4xx` не повторяется. Редиректы не преследуются: клиент просит указать
конечный `https`-адрес в `--server`, код 2.

Пример с машиночитаемым выводом и своим таймаутом:

```bash
uv run patches-please scan \
  --provider github --commit "$GITHUB_SHA" --ref "$GITHUB_REF" \
  --wait --json --timeout 600
```

## Вывод

Человекочитаемый режим печатает прогон, статус и вердикт. Ещё две строки —
«Находки по severity» и «Отчёт» — остаются пометкой: этих полей в ответе API
(`ScanResponse`) нет. Находки видны на странице прогона в интерфейсе, а отчёты
worker пишет файлами `<scan_id>.json` и `<scan_id>.html` в каталог `REPORTS_DIR`
(по умолчанию `reports/`). С `--json` в stdout уходит ровно один JSON-объект
прогона, диагностика — в stderr. Токен не печатается ни в одном режиме,
включая `--verbose` и сообщения об ошибках.

## Ограничения MVP

- Для реального прогона нужен развёрнутый сервис с worker: без него `--wait`
  вернёт 5 или 6, а действие упадёт. Инструкция по развёртыванию — T-033
  (`docs/runbook.md`), она ещё не написана.
- Находки и адрес отчёта в ответе API отсутствуют, поэтому клиент печатает
  на их месте пометку. Сами отчёты и находки уже есть: страница прогона,
  JSON и HTML в каталоге отчётов.
- Повторный `POST` того же коммита возвращает существующий прогон при любом
  статусе, включая `error`: перезапуск job не создаст новый прогон. Это
  ограничение сервиса (T-009), а не клиента.
- `--fail-on-degraded` принимается, но пока ничего не передаёт: поля в API нет.
  Клиент пишет предупреждение в stderr и не меняет вердикт — его считает
  политика проекта.
- Самоподписанный стенд требует системного доверия к сертификату: флага
  `--insecure` в MVP нет.
- Демо-воркфлоу `.github/workflows/demo-scan.yml` запускается вручную: пока
  стенд не развёрнут, он падает на подключении к сервису.
