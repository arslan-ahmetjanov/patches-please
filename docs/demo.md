# Демо-стенд: репозиторий, данные и прогон

Инструкция для T-032 (CON-003): как опубликовать демо-репозиторий с учебными
уязвимостями, заполнить стенд и получить находки всех трёх сканеров. Данные
работодателя не используются ни на одном шаге: демо-репозиторий состоит из
вымышленного кода и фиктивного секрета.

## Что входит в демо

| Файл основного репозитория | Назначение |
| --- | --- |
| `demo/README.md` | README демо-репозитория: предупреждение, таблица находок, ограничения |
| `demo/LICENSE` | Лицензия MIT демо-репозитория, как у остальных учебных репозиториев |
| `demo/app.py` | Учебный сервис: `eval`, `subprocess` с `shell=True`, `pickle.loads`, фиктивный токен |
| `demo/requirements.txt` | Устаревшие зависимости для Trivy |
| `scripts/seed_demo.py` | Идемпотентное заполнение: пользователь, проект, токен, baseline |
| `docs/demo.md` | Этот документ |

В `demo/` лежит исходник отдельного публичного репозитория. В основном репозитории
он лежит для ревью и версионирования (CON-003), а worker проверяет копию,
опубликованную по `repo_url`.

## Почему репозиторий отдельный

Worker клонирует проект по адресу `projects.repo_url` во временный каталог
(`patches_please/scans/pipeline.py`). Локальный путь или смонтированный каталог
ему недоступны: контейнер получает только URL. Поэтому демо-код публикуется
отдельным публичным репозиторием, а в проекте указывается его HTTPS-адрес.

Репозиторий должен быть публичным: учётных данных для клонирования у worker
нет, и приватный адрес даст прогон со статусом `error`.

Рекомендуем имя `arslan-ahmetjanov/patches-please-demo`. Другой аккаунт и
имя допустимы: адрес задаётся переменной `DEMO_REPO_URL`.

## 1. Опубликовать демо-репозиторий

Команды для Git Bash или WSL. Нужен авторизованный [GitHub CLI](https://cli.github.com/).

```bash
tmp="$(mktemp -d)"
cp -r demo/. "$tmp"/
cd "$tmp"
git init -b main
git add .
git commit -m "feat: демо-репозиторий с учебными уязвимостями"
gh repo create arslan-ahmetjanov/patches-please-demo --public --source . --push
git rev-parse HEAD
```

Последняя команда печатает SHA коммита, он понадобится для запуска прогона.
Если репозиторий уже создан, вместо `gh repo create` добавьте remote и
отправьте изменения:

```bash
git remote add origin https://github.com/arslan-ahmetjanov/patches-please-demo.git
git push -u origin main
```

При изменении `demo/` в основном репозитории повторите публикацию: источник
правды здесь каталог `demo/`, а не ручные правки в демо-репозитории.

## 2. Подготовить стенд

```bash
docker compose up -d --build
curl http://localhost:8000/health
uv run alembic upgrade head
```

Ожидаемый ответ `/health`: `{"status":"ok"}`. Миграции запускаются с хоста и
по умолчанию идут на `localhost:5432` (значение из `patches_please/db.py`).

Если в оболочке экспортирован `DATABASE_URL` из `.env`, он указывает на хост
`postgres` и с хоста не разрешается. Для скрипта заполнения задайте локальный
адрес явно:

```bash
export DATABASE_URL='postgresql+psycopg://patches_please:patches_please_local@localhost:5432/patches_please'
```

## 3. Заполнить демо-данные

Скрипт работает с базой напрямую: регистрации в API нет, а baseline ставится
сервисной функцией. Пароль и адрес репозитория берутся только из окружения,
в файлах репозитория их нет.

| Переменная | Обязательна | Значение по умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | нет | локальный стенд из `patches_please/db.py` |
| `DEMO_EMAIL` | нет | `demo@example.com` |
| `DEMO_PASSWORD` | да | нет; не короче 8 символов |
| `DEMO_PROJECT_NAME` | нет | `Демо: сервис Заметки` |
| `DEMO_PROJECT_SLUG` | нет | `patches-please-demo` |
| `DEMO_REPO_URL` | да | нет |
| `DEMO_DEFAULT_BRANCH` | нет | `main` |
| `DEMO_TOKEN_NAME` | нет | `ci` |

```bash
export DEMO_PASSWORD='<пароль демо-пользователя>'
export DEMO_REPO_URL='https://github.com/arslan-ahmetjanov/patches-please-demo.git'
uv run python scripts/seed_demo.py
```

PowerShell:

```powershell
$env:DEMO_PASSWORD = "<пароль демо-пользователя>"
$env:DEMO_REPO_URL = "https://github.com/arslan-ahmetjanov/patches-please-demo.git"
uv run python scripts/seed_demo.py
```

Пример вывода (значение токена будет другим):

```text
пользователь создан: demo@example.com
проект создан: patches-please-demo (2f1c…)
токен создан: ci (9a4e…)

демо-стенд готов: пользователь demo@example.com, проект patches-please-demo (2f1c…)
токен проекта (показывается один раз): pp_…
дальше: запустите прогон по коммиту демо-репозитория — см. docs/demo.md
```

Что делает скрипт:

- создаёт пользователя или приводит пароль существующего к `DEMO_PASSWORD`;
- создаёт проект с адресом репозитория и членство `owner` либо обновляет
  название, `repo_url` и ветку существующего проекта;
- выпускает токен CI, если действующего токена с этим именем нет. Открытое
  значение печатается один раз: в базе хранится только SHA-256;
- baseline не трогает, пока не передан `--baseline-latest` или `--baseline-scan`.

Повторный запуск с теми же параметрами не создаёт дублей. Пароль существующего
пользователя обновляется до значения из окружения, так демо-вход гарантированно
работает после смены пароля.

Если стенд уже заполнялся, вывод отличается от примера: строки «создан»
сменяются на «найден», а токен выглядит так:

```text
пользователь найден: demo@example.com
проект найден: patches-please-demo (3413d8ab-…)
токен «ci» уже действует; открытое значение не хранится. Новый можно выпустить с --rotate-token
```

Открытое значение в базе не хранится, поэтому на существующем стенде токен для
прогона получают через `--rotate-token`: действующие токены с именем `ci`
отзываются, выпускается один новый. Тот же флаг нужен, если старое значение
попало в лог терминала.

## 4. Запустить прогон

Токен из вывода скрипта передайте клиенту. По умолчанию клиент обращается к
`http://localhost:8000`. Если `API_PORT` в `.env` отличается (на Windows 8000
попадает в зарезервированный диапазон, поэтому там стоит 8081), адрес
задаётся флагом `--server` или переменной `PATCHES_PLEASE_URL`:

```bash
export PATCHES_PLEASE_URL='http://localhost:8081'
```

```bash
export PATCHES_PLEASE_TOKEN='pp_…'
uv run patches-please scan \
  --provider github \
  --commit <полный SHA демо-коммита> \
  --ref main \
  --wait
```

Коды выхода: `0` это `pass`, `1` это `fail`, `2` ошибка аргументов, `3` нет
доступа, `4` прогон завершился `error`, `5` истёк таймаут, `6` сеть.
Первый прогон на демо должен завершиться кодом `1`.

Тот же запуск через API:

```bash
curl -sS -X POST http://localhost:8000/api/v1/scans \
  -H "Authorization: Bearer $PATCHES_PLEASE_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"commit_sha":"<полный SHA>","ref":"main","provider":"github"}'

curl -sS http://localhost:8000/api/v1/scans/<scan_id> \
  -H "Authorization: Bearer $PATCHES_PLEASE_TOKEN"
```

Повторный `POST` с тем же проектом и коммитом возвращает существующий прогон,
а не создаёт новый. Чтобы получить второй результат, нужен новый коммит.

## 5. Ожидаемый результат первого прогона

| Сканер | Тип | Находка | Уровень в отчёте |
| --- | --- | --- | --- |
| Semgrep | SAST | `…python.eval` в `app.py` | medium |
| Semgrep | SAST | `…python.subprocess-shell-true` в `app.py` | medium |
| Semgrep | SAST | `…python.pickle-loads` в `app.py` | medium |
| Gitleaks | секреты | `generic-api-key` в `app.py` | medium |
| Trivy | зависимости | уязвимости в `requests`, `PyYAML`, `Jinja2`; на проверке их 11 | high и medium |

Точное число находок Trivy зависит от базы уязвимостей, зашитой в образ worker
при сборке. На базе Trivy от 25.11.2026 демо-набор даёт 11 уязвимостей:
`critical` у CVE-2020-14343 в PyYAML 5.3.1, уровень `high` у CVE-2019-10906 в Jinja2
2.10, остальные `medium`. Все три класса находок при этом присутствуют: SAST, секреты
и зависимости (FR-002).

Прогон на стенде 27.11.2026 дал 15 находок: 3 SAST, 1 секрет и 11 зависимостей;
вердикт `fail`, код выхода клиента 1.

Идентификатор правила Semgrep содержит путь конфигурации: при каталоге
`/opt/semgrep-rules` в отчёте будет, например,
`opt.semgrep-rules.semgrep.patches-please.python.eval`. Суффикс
`semgrep.patches-please.python.*` стабилен: он повторяет путь
`scanner-rules/semgrep/patches-please/python/*.yml` в образе worker. Префикс
зависит от каталога правил. Уровни Semgrep и Gitleaks в отчёте равны `medium`: их
SARIF не заполняет `level` результата, и нормализатор применяет умолчание.
Trivy пишет `error` для своих `critical` и `high`; нормализатор переводит
`error` в `high`, поэтому в отчёте видны `high`, а не `critical`.

Сообщение находки-секрета в отчёте заменено заглушкой `[секрет скрыт]`
(NFR-004), правило, путь и строка остаются.

Политика по умолчанию блокирует `critical` и `high`, поэтому первый прогон
получает вердикт `fail` (S-002): высокие находки Trivy новые и не покрыты baseline.
Это ожидаемое поведение, а не ошибка настройки.

Находки, вердикт, метрики и отчёты видны на странице прогона и в артефактах
worker (`REPORTS_DIR`, по умолчанию `/app/reports`).

## 6. Сценарий baseline: `pass` на тех же находках

Baseline фиксирует текущий шум, чтобы исторические находки не блокировали
разработку (FR-006, S-003). Ставится он только по завершённому прогону.

```bash
export DEMO_PASSWORD='<тот же пароль>'
export DEMO_REPO_URL='https://github.com/arslan-ahmetjanov/patches-please-demo.git'
uv run python scripts/seed_demo.py --baseline-latest
```

Проверить конкретный прогон можно флагом `--baseline-scan <uuid>`. Baseline
проекта один: повторная установка заменяет набор fingerprints, а не создаёт
вторую запись.

Затем внесите в демо-репозиторий безопасное изменение, например поправьте
пунктуацию в его `README.md` (в основном репозитории это `demo/README.md`), и
опубликуйте новый коммит. Запустите прогон на новом SHA:

```bash
uv run patches-please scan \
  --provider github \
  --commit <новый SHA> \
  --ref main \
  --wait
```

Ожидаемый результат: код `0` и вердикт `pass`. Все находки совпали с baseline
и получили состояние `existing`. Так проходят S-001 (проверка не мешает релизу)
и S-003 (legacy-проект не блокируется целиком).

Если изменить сам `app.py`, fingerprint находки может измениться: в него входит
фрагмент кода, но не номер строки. Безопасная правка README этого не делает.

## 7. Проверка перед показом (CON-003)

- В `demo/` нет данных работодателя, названий организаций и внутренних адресов.
- В `demo/app.py` лежит заглушка секрета `pp_…`; она не зарегистрирована ни в одном
  сервисе. Настоящие ключи и токены не используются.
- Зависимости из `demo/requirements.txt` не устанавливаются: Trivy читает
  манифест, код библиотек не запускается.
- Приложение не разворачивается: опасные вызовы не выполняются.
- В отчётах прогона значение секрета замаскировано.

Быстрая проверка демо-каталога:

```bash
grep -RniE 'заказчик|работодател|@[a-z0-9.-]+\.(ru|com)' demo/
grep -Rn 'API_TOKEN' demo/
```

Первая команда не должна находить совпадений. Вторая находит только строку с
фиктивной константой в `demo/app.py`.

## 8. Ограничения

- Trivy использует базу, зашитую в образ при сборке (`--skip-db-update`).
  После пересборки число находок может измениться: база новее, поэтому находок больше.
- Набор правил Semgrep минимальный и лежит в `scanner-rules/semgrep`; реестр
  `p/...` в офлайне недоступен.
- Gitleaks сканирует рабочее дерево клона, а не историю git: проверяется
  текущий коммит.
- Baseline ставится скриптом напрямую в базу: отдельного метода REST API нет.
- Демо-репозиторий должен быть публичным, иначе клон в worker не пройдёт.

## 9. Уборка

```bash
docker compose down -v
```

`-v` удаляет тома PostgreSQL, Redis и отчётов вместе с демо-данными. Без `-v`
пользователь, проект и прогоны остаются на месте, и повторный запуск скрипта
продолжит с существующими записями.
