# Сканеры: версии, запуск и офлайн-режим

Документ описывает образ worker с тремя сканерами (T-013, FR-002, FR-030,
NFR-003). API-образ сканеров не содержит: `Dockerfile` остаётся лёгким, а
`Dockerfile.worker` собирает отдельный образ с бинарниками, правилами и базой.

## Состав

| Сканер | Тип проверки | Версия | Лицензия | Что проверяет |
| --- | --- | --- | --- | --- |
| Semgrep | SAST | 1.186.0 | LGPL-2.1 | Небезопасные вызовы в коде (локальные правила) |
| Gitleaks | Секреты | 8.30.1 | MIT | Секреты в файлах рабочего каталога |
| Trivy | Зависимости | 0.76.2 | Apache-2.0 | Уязвимости в манифестах зависимостей |

Версии зафиксированы 22.11.2026. База Trivy в образе: `UpdatedAt`
2026-11-22T12:38:44Z, `DownloadedAt` 2026-11-22T16:27:44Z. Итоговую проверку
разрешительности лицензий делает T-031 (`docs/licenses.md`); здесь указаны
лицензии самих инструментов.

## Как сканеры попадают в образ

`Dockerfile.worker` собирается на той же базе, что и API
(`ghcr.io/astral-sh/uv:python3.12-bookworm-slim`), но добавляет:

- **Semgrep**: точная версия из PyPI в отдельное окружение `/opt/semgrep`,
  чтобы его зависимости не конфликтовали с зависимостями приложения.
  Версия задаётся `ARG SEMGREP_VERSION`.
- **Gitleaks и Trivy**: закреплённые релизы с GitHub. Для каждой архитектуры
  (`amd64`, `arm64`) в `Dockerfile.worker` лежит свой `ARG` с SHA256; скачивание
  проверяется `sha256sum -c` до распаковки.
- **Правила Semgrep**: каталог `scanner-rules/semgrep` из репозитория
  копируется в `/opt/semgrep-rules`. Реестр `p/...` не используется: он требует
  сети.
- **База Trivy**: скачивается при сборке командой
  `trivy fs --download-db-only --cache-dir /opt/trivy-cache` и остаётся в образе.
  Рантайм работает с `--skip-db-update`.
- **Версии инструментов**: `/opt/scanner-versions.json` создаётся из тех же
  `ARG`, что и установка. Это источник `tool_version` для Semgrep и Gitleaks,
  которые не пишут версию в SARIF.

Контейнер работает от пользователя `app` (uid 10001) с домашним каталогом:
Semgrep использует его для кеша. `docker.sock` в образ не пробрасывается.

## Команды запуска

Адаптеры вызывают инструменты списком аргументов, без `shell=True`
(`patches_please/scanners/process.py`). Содержимое stdout/stderr не читается и не пишется в
лог: оно может содержать секреты (NFR-004).

| Сканер | Команда |
| --- | --- |
| Semgrep | `semgrep scan --config /opt/semgrep-rules --sarif --output <out>/semgrep.sarif --metrics=off --disable-version-check --quiet <workdir>` |
| Gitleaks | `gitleaks dir <workdir> --report-format sarif --report-path <out>/gitleaks.sarif --no-banner --redact` |
| Trivy | `trivy fs <workdir> --format sarif --output <out>/trivy.sarif --scanners vuln --cache-dir /opt/trivy-cache --skip-db-update --skip-java-db-update --quiet` |

Почему так:

- `--metrics=off` и `--disable-version-check` убирают обращения Semgrep в сеть.
- `gitleaks dir` сканирует файлы, а не историю git: worker получает клон
  `--depth 1`, а проверяется текущий коммит. `--redact` маскирует секрет в
  собственном отчёте Gitleaks, а сообщение находки типа `secrets` заменяется
  заглушкой при нормализации (T-021, NFR-004).
- `trivy fs` проверяет манифесты зависимостей в рабочем каталоге. `--scanners
  vuln` оставляет только уязвимости: секреты ищет Gitleaks, конфигурации
  инфраструктуры в FR-002 не входят.
- `--skip-db-update` и `--skip-java-db-update` запрещают сетевые обновления баз.

## Код возврата и статус

Код возврата инструмента сам по себе не признак успеха: Semgrep и Gitleaks
возвращают 1 при находках. Успех (`ok`) требует допустимого кода **и** валидного SARIF
2.1.0 с непустым `runs`. Иначе адаптер возвращает `failed` с причиной без вывода
инструмента.

| Сканер | Допустимые коды | Что означает код |
| --- | --- | --- |
| Semgrep | 0, 1 | 0 это чисто, 1 это находки, 2 и выше сбой |
| Gitleaks | 0, 1 | 0 это чисто, 1 это находки или ошибка; SARIF отличает одно от другого |
| Trivy | 0 | Находки не меняют код; любой другой код сбой |

Таймаут подпроцесса даёт статус `timed_out`; отсутствующий бинарник, недопустимый
код, отсутствующий или битый SARIF дают `failed`. Общий таймаут сканеров (300 с,
FR-028) передаётся каждому адаптеру; по истечении завершается группа процессов
целиком, включая дочерний `semgrep-core`.

## Версия инструмента

`ScannerRun.tool_version` берётся из `runs[0].tool.driver.version`, если
инструмент заполнил это поле (так делает Trivy), иначе из
`/opt/scanner-versions.json`. Файл создаётся при сборке из тех же `ARG`, что и
установка инструментов. Отдельный `--version` не запускается: в офлайне Semgrep
печатает версию, но не завершается: фоновый процесс держит унаследованный
пайп, и запрос повисает до таймаута. Версию считаем метаданными: её отсутствие не
делает запуск неуспешным.

## Офлайн-прогон

Сеть нужна только при сборке образа: PyPI, GitHub Releases и
хранилище базы Trivy.

```bash
docker build -f Dockerfile.worker -t patches-please-worker:local .
docker run --rm --network none \
  -v "$PWD/tests/fixtures/scanner-repo:/src:ro" \
  patches-please-worker:local \
  python -m patches_please.scanners.offline \
  --workdir /src --output /tmp/artifacts --require-findings
```

В Windows `cmd` путь монтируется как `-v "%CD%\tests\fixtures\scanner-repo:/src:ro"`.
Каталог SARIF можно не монтировать: проверка печатает сводку и удаляет контейнер.

Ожидаемый результат: JSON с `"ok": true` и тремя записями `"status": "ok"`.
`--require-findings` дополнительно требует хотя бы одну находку от каждого
сканера; фикстура `tests/fixtures/scanner-repo` содержит вымышленные
небезопасные вызовы, секрет и устаревшие зависимости. Содержимое находок в
сводку не выводится, там только счётчики.

NFR-003 проверяем запуском с `--network none`: правила Semgrep и база Trivy уже
внутри образа, поэтому прогон не обращается в интернет.

## Порядок обновления

1. **Версия инструмента.** Изменить `ARG` в `Dockerfile.worker`. Для Gitleaks и
   Trivy взять SHA256 нужной архитектуры из ассетов релиза и обновить
   `GITLEAKS_SHA256_*` / `TRIVY_SHA256_*`. Файл `/opt/scanner-versions.json`
   обновится сам: он собирается из этих же `ARG`. Пересобрать образ и прогнать
   офлайн-проверку.
2. **Правила Semgrep.** Добавить или изменить YAML в `scanner-rules/semgrep`.
   Идентификаторы правил должны быть уникальны; после правки нужны пересборка и
   офлайн-проверка на фикстуре. Правила не скачиваются во время работы.
3. **База Trivy.** Обновляется при пересборке: изменить `ARG TRIVY_DB_REVISION`
   (дата) и собрать образ заново: сбросится кеш только слоя с базой. Дата базы
   проверяется в контейнере:
   `docker run --rm patches-please-worker:local cat /opt/trivy-cache/db/metadata.json`.
4. **Дата фиксации.** После обновления версий или базы обновить таблицу
   «Состав» и дату в этом документе.

## Ограничения

- Набор правил Semgrep минимальный и лежит в репозитории. Это осознанный
  компромисс: полный реестр `p/...` требует сети, а копия реестра сильно
  увеличивает образ. Расширение делается добавлением файлов в `scanner-rules/semgrep`.
- Trivy проверяет файловую систему, а не образ контейнера: в V1 сканируется
  исходный код репозитория. Сканирование образов выходит за FR-002 текущего объёма.
- Java DB не скачивается (`--skip-java-db-update`): уязвимости Java-зависимостей
  в этой конфигурации не проверяются.
- База Trivy не обновляется между пересборками: офлайн-режим важнее свежести.
  Периодичность пересборки задаётся эксплуатацией.
- Сообщение находки типа `secrets` маскируется при нормализации: в БД и в оба
  отчёта попадает заглушка `[секрет скрыт]`, правило, путь и строка остаются
  (T-021, NFR-004). Gitleaks дополнительно маскирует секрет в своём SARIF
  (`--redact`). Уже сохранённые находки и отчёты прошлых прогонов не
  переписываются.

## Проверка

```bash
uv run pytest tests/test_process.py tests/test_adapters.py tests/test_offline.py
docker run --rm --network none \
  -v "$PWD/tests/fixtures/scanner-repo:/src:ro" \
  patches-please-worker:local \
  python -m patches_please.scanners.offline --workdir /src --output /tmp/artifacts --require-findings
```

Тесты покрывают команды, коды возврата, таймаут, отказ запуска, отсутствующий и
битый SARIF, а также правило успеха офлайн-проверки. Реальный офлайн-прогон
запускается вручную: Docker в CI-джобах T-013 не собирается.
