# CI на GitLab CI

Шаблон job `ci/gitlab/patches-please.yml` (T-027) ставит тот же CLI
`patches-please`, что и действие GitHub Actions, и делает ровно один вызов:

```bash
patches-please scan --provider gitlab --commit "$CI_COMMIT_SHA" --ref "$CI_COMMIT_REF_NAME" --wait
```

Ожидание, повторы и перевод вердикта в код выхода выполняет клиент (delta-008).
Собственного цикла опроса в шаблоне нет, `|| true` не используется, поэтому
код выхода клиента становится кодом выхода job: `fail` роняет job, `pass`
пропускает (FR-019, FR-020, FR-033). Устройство клиента, коды выхода и вывод
подробно описаны в [ci-github.md](ci-github.md), они одинаковы для обоих CI.

## Шаблон

Файл `ci/gitlab/patches-please.yml` определяет скрытый job `.patches-please`.
Его подключают через `include` и наследуют через `extends`:

```yaml
include:
  - local: ci/gitlab/patches-please.yml

stages:
  - test

patches-please:
  extends: .patches-please
  stage: test
  when: manual
  allow_failure: true
```

Такой файл уже лежит в корне репозитория как `.gitlab-ci.yml`. В других
проектах путь в `include: local` указывает на файл внутри их репозитория;
шаблон можно скопировать или подключить по `include: remote`/`project`.

`when: manual` и `allow_failure: true` выбраны намеренно: пока сервис не
развёрнут, прогон не пройдёт, а пайплайн на каждый push падать не должен.
Ручной job не запускается сам. После запуска job получает код выхода клиента:
`fail` делает статус job красным, но из-за `allow_failure: true` пайплайн
остаётся успешным. Для блокирующего гейта уберите `allow_failure` и
`when: manual` (см. «Ограничения MVP»).

## Настройка проекта

1. Создайте токен проекта. Токен выдаётся один раз в ответе
   `POST /api/v1/projects/{project_id}/tokens` (создавать может владелец
   проекта); значение имеет вид `pp_...` и больше не показывается.
2. Откройте Settings → CI/CD → Variables и добавьте две переменные:

   | Имя | Значение | Настройки |
   | --- | --- | --- |
   | `PATCHES_PLEASE_URL` | адрес сервиса, например `https://patches.example.ru` | visible; укажите полный `http(s)`-URL без `/api/v1` |
   | `PATCHES_PLEASE_TOKEN` | токен `pp_...` | **masked** и **protected** |

   `masked` скрывает значение в логах job. `protected` не отдаёт переменную
   pipeline-ам незащищённых веток и тегов; так шаблон защищает токен от утечки через
   merge request из форка. Если job должен работать и на незащищённой ветке,
   снимите `protected` осознанно: токен станет доступен более широкому кругу
   запусков.
3. Не записывайте значения в `.gitlab-ci.yml`: файл хранится в репозитории,
   а токен в нём держать нельзя. Шаблон читает обе переменные из окружения job.

Для маскирования GitLab требует, чтобы значение было не короче восьми символов
без пробелов и переводов строк; токены `pp_...` этому соответствуют.

Если репозиторий с клиентом приватный (сейчас
`arslan-ahmetjanov/patches-please` закрыт), добавьте ещё одну переменную:

| Имя | Значение | Настройки |
| --- | --- | --- |
| `PATCHES_PLEASE_CLI_TOKEN` | GitHub fine-grained token с правом `Contents: read` на репозиторий клиента | **masked** и **protected** |

Токен нужен только для клона клиента. Шаблон передаёт его git через
`GIT_ASKPASS`, а не через URL: значение не попадает в аргументы команды,
в `.git/config` и в вывод ошибок, а в логах его скрывает masked. Для публичного
репозитория переменную не задавайте, клон пройдёт без аутентификации.

## Переменные

| Переменная | Где задаётся | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `PATCHES_PLEASE_URL` | CI/CD-переменная проекта | нет | Адрес API сервиса, `http(s)://host[:port]` |
| `PATCHES_PLEASE_TOKEN` | CI/CD-переменная проекта, masked | нет | Токен проекта `pp_...` |
| `PATCHES_PLEASE_CLI_TOKEN` | CI/CD-переменная проекта, masked | нет | Токен на чтение репозитория клиента; нужен, только если репозиторий приватный |
| `PATCHES_PLEASE_CLI_REPO` | шаблон | `https://github.com/arslan-ahmetjanov/patches-please.git` | Репозиторий, откуда ставится CLI |
| `PATCHES_PLEASE_CLI_REF` | шаблон | полный SHA коммита с клиентом | Закреплённый ref: полный SHA или тег |
| `PATCHES_PLEASE_CLI_DIR` | шаблон | `.patches-please-cli` | Каталог клона внутри workspace job |
| `PATCHES_PLEASE_TIMEOUT` | шаблон | `900` | Общий дедлайн клиента в секундах |
| `CI_COMMIT_SHA` | GitLab, предопределённая | нет | Полный SHA проверяемого коммита, уходит в `--commit` |
| `CI_COMMIT_REF_NAME` | GitLab, предопределённая | нет | Имя ветки или тега, уходит в `--ref` |

Переменные job и проекта переопределяют значения из шаблона. Например, чтобы
поставить другую версию клиента, задайте `PATCHES_PLEASE_CLI_REF` в CI/CD-
переменных или в `variables` своего job.

`CI_COMMIT_SHA` указывает на коммит, для которого запущен pipeline. Если в проекте
включены merged results pipelines, GitLab подставляет SHA коммита слияния,
а не вершину исходной ветки; для проверки именно ветки отключите merged
results или измените шаблон под свой сценарий. Для merge request pipeline
`CI_COMMIT_REF_NAME` даёт имя исходной ветки.

## Как это работает

- Образ `python:3.12-slim`. В `before_script` ставятся `git` и
  `ca-certificates`, затем `uv` фиксированной версии `0.13.9` через `pip`.
  Версия `uv` закреплена, чтобы установка не зависела от содержимого образа.
- CLI клонируется из `PATCHES_PLEASE_CLI_REPO` на закреплённый
  `PATCHES_PLEASE_CLI_REF`: `git init`, `fetch --depth 1` по SHA,
  `checkout --detach FETCH_HEAD`. Плавающая ветка не используется.
  Публикации в PyPI нет, поэтому пакет ставится из дерева репозитория.
  Если задан `PATCHES_PLEASE_CLI_TOKEN`, git получает его через
  `GIT_ASKPASS`; в URL и аргументах команды токена нет.
- `uv sync --frozen --no-dev` ставит клиента и его зависимости по `uv.lock`;
  dev-группа и серверные зависимости в job не нужны.
- `script` содержит один вызов `patches-please scan --wait --timeout 900`.
  Токен передаётся флагом `--token` и не печатается; в логах его скрывает
  настройка masked у CI/CD-переменной.
- `timeout: 20m` у job больше дедлайна клиента: запас на установку и клон.
- В шаблоне нет `|| true` и нет цикла ожидания: ожидание работает только через
  `--wait`, а вердикт берётся только из ответа API.

Шаблон рассчитан на GitLab Runner с Docker-исполнителем: job использует
образ. Раннеру нужен доступ в сеть: к GitHub (клон клиента), PyPI (uv и
зависимости) и к сервису Patches, Please.

## Коды выхода

| Код | Значение |
| --- | --- |
| 0 | вердикт `pass` (или прогон только запущен без `--wait`) |
| 1 | вердикт `fail` |
| 2 | ошибка аргументов или адреса: нет провайдера, коммита, ref или токена; неверные `--server`, `--timeout`, `--interval`; `3xx`; `404` на старте; `4xx` от API |
| 3 | `401`, `403` или `404` при опросе: нет доступа к прогону |
| 4 | `status=error`, завершение без вердикта или неполный ответ сервиса |
| 5 | истёк `--timeout` в ожидании |
| 6 | сеть, `5xx` после повторов или непредвиденная ошибка клиента |

GitLab считает job упавшим при любом ненулевом коде, поэтому `1` (находки
блокирующего уровня) и `2…6` (сбой проверки) в интерфейсе выглядят одинаково.
Различить их можно по коду в логе job и по сообщению клиента в stderr.

Код 2 в начале job шаблон возвращает и сам, когда не заданы
`PATCHES_PLEASE_URL`, `PATCHES_PLEASE_TOKEN`, `CI_COMMIT_SHA` или
`CI_COMMIT_REF_NAME`. Это та же категория «ошибка настройки», что и у клиента.

## Отличия от GitHub Actions

| | GitHub Actions | GitLab CI |
| --- | --- | --- |
| Подключение | `uses: ./.github/actions/patches-please` | `include: local` + `extends: .patches-please` |
| Откуда ставится CLI | копия репозитория действия (`github.action_path`) | клон канонического репозитория на закреплённый SHA |
| Доступ к репозиторию клиента | даёт GitHub при загрузке действия | анонимно для публичного, `PATCHES_PLEASE_CLI_TOKEN` для приватного |
| Маскирование токена | `::add-mask::` в действии | настройка masked у CI/CD-переменной |
| Запуск демо | `workflow_dispatch` в `demo-scan.yml` | `when: manual` у job |
| Область секретов | secrets репозитория или environment | CI/CD-переменные проекта, `protected` ограничивает ветки |
| Ожидание и код выхода | `scan --wait`, код клиента | `scan --wait`, код клиента |

Логика в обоих случаях одна: обёртка только ставит клиент и вызывает `scan`
один раз. Ни в действии, ни в шаблоне нет собственного поллинга.

## Локальная проверка

Проверка конфигурации без запуска job:

```bash
npx --yes gitlab-ci-local --list
```

Команда должна показать job `patches-please` со стадией `test` и
`when: manual`, без ошибок схемы и include. `gitlab-ci-local` ищет локальный
include среди файлов, известных git, поэтому новый шаблон должен быть
добавлен в индекс (`git add`), иначе будет ошибка
`Local include file cannot be found`.

Полный прогон job:

```bash
npx --yes gitlab-ci-local --manual patches-please \
  --variable PATCHES_PLEASE_URL=http://host.docker.internal:8080 \
  --variable PATCHES_PLEASE_TOKEN=pp_local_check \
  --variable PATCHES_PLEASE_CLI_REF=<полный SHA клиента>
```

Если репозиторий клиента приватный, добавьте
`--variable PATCHES_PLEASE_CLI_TOKEN=<токен>`; без него клон остановится на
запросе логина. Локальный токен одноразовый и годится только для проверки.

Нужны запущенный Docker и доступ в сеть. Вместо развёрнутого сервиса можно
поднять на хосте HTTP-stub, который на `POST /api/v1/scans` отвечает
`200`/`202` с завершённым прогоном, например
`{"id": "<uuid>", "status": "done", "verdict": "pass"}`: клиент увидит
терминальный статус и выйдет с кодом 0. С `verdict: "fail"` job завершится
кодом 1: в логе `gitlab-ci-local` это строка `finished ... WARN 1`, но процесс
`gitlab-ci-local` вернёт 0, потому что ручной job объявлен с
`allow_failure: true`. Адрес `host.docker.internal` доступен из контейнера
Docker Desktop; на Linux-хосте используйте адрес docker-моста.

## Ограничения MVP

- Для реального прогона нужен развёрнутый сервис с worker. Без него `--wait`
  вернёт 5 или 6, а job упадёт. Инструкцию по развёртыванию пишет T-033
  (`docs/runbook.md`), она ещё не написана.
- Находки и адрес отчёта в ответе API отсутствуют, поэтому клиент печатает
  на их месте пометку. Сами отчёты и находки есть на странице прогона и в
  файлах `<scan_id>.json`/`<scan_id>.html` в каталоге отчётов worker.
- Повторный `POST` того же коммита возвращает существующий прогон при любом
  статусе, включая `error`: перезапуск job не создаст новый прогон.
- `--fail-on-degraded` принимается, но пока ничего не передаёт: поля в API нет.
- Самоподписанный стенд требует системного доверия к сертификату: флага
  `--insecure` в MVP нет.
- Закреплённый SHA должен существовать в удалённом репозитории: клон идёт по
  сети. При обновлении клиента меняйте `PATCHES_PLEASE_CLI_REF` вместе с
  выпуском, а не переходите на плавающую ветку.
- Репозиторий клиента сейчас приватный. Без `PATCHES_PLEASE_CLI_TOKEN` клон
  в job остановится на запросе логина и завершится ошибкой; для публичного
  репозитория переменная не нужна.
- Ручной job с `allow_failure: true` не блокирует пайплайн ни до, ни после
  запуска: при `fail` краснеет только job. Если нужен обязательный гейт,
  уберите `when: manual` и `allow_failure` после того, как сервис развёрнут.
- Токен в protected-переменной не попадёт в pipeline незащищённой ветки или
  merge request из форка, такой job завершится кодом 2 с сообщением о
  незаданной переменной.
