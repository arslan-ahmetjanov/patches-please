# Чек-лист защиты

Одна страница: что поднять, что открыть и что показать. Проверено на стенде
27.11.2026.

## За день до защиты

1. `docker desktop start`, затем `docker compose up -d --build`. Дождаться
   `curl http://localhost:8081/health` → `{"status":"ok"}`. Docker Desktop на
   этой машине засыпает при простое, после старта порты появляются не сразу.
2. `uv run alembic upgrade head`: миграции применяются с хоста.
3. Заполнить стенд: `DEMO_PASSWORD=... DEMO_REPO_URL=https://github.com/arslan-ahmetjanov/patches-please-demo.git uv run python scripts/seed_demo.py --rotate-token`.
   Токен печатается один раз, сохранить его в переменную окружения.
4. Прогнать сценарий целиком на свежих данных: прогон на старом коммите даёт
   код `1` и вердикт `fail`, `--baseline-latest`, новый коммит, прогон даёт код
   `0` и `pass`.
5. Открыть `docs/screenshots/` и убедиться, что снимки соответствуют текущему
   интерфейсу. Если правили шаблоны, пересобрать образы и снять заново.
6. Проверить `demo-scan.yml`: либо задан `PATCHES_PLEASE_URL` и последний job
   зелёный, либо готов рассказ, что интеграция проверена локально, а публичного
   адреса у стенда нет.

## За час

- Docker Desktop запущен, `docker compose ps` показывает четыре контейнера
  `healthy`.
- Открыты вкладки: `/projects`, страница демо-проекта, страница прогона,
  настройки, GitHub Actions (зелёный CI), Dependabot (открытых алертов 0).
- В терминале готов адрес API (`http://localhost:8081`) и переменная с токеном.
- Пароль демо-пользователя под рукой.

## На защите, по шагам

1. Проблема: проверки безопасности вручную и нерегулярно, узнаём поздно.
2. Прогон на старом коммите: код выхода `1`, вердикт `fail`. В отчёте три
   класса находок: SAST, секрет, уязвимые зависимости.
3. Секрет в отчёте замаскирован: `[секрет скрыт]`, правило и место видны.
4. Baseline: те же находки получают состояние `existing`, новый коммит проходит
   с кодом `0` и вердиктом `pass`.
5. Гейт в CI: клиент возвращает код по вердикту, пайплайн блокируется без
   ручных действий. Композитное действие GitHub и шаблон GitLab делают один и
   тот же вызов.
6. Ограничения назвать самому: три правила Semgrep, база Trivy зашита в образ,
   демо-манифест уязвим намеренно.

## Если что-то упало

- Docker не поднялся: показывать по скриншотам `docs/screenshots/` и
  HTML-отчёту, восстановленный стенд не обязателен.
- API не отвечает: отчёт и логи worker (`docker compose logs worker`) объясняют
  причину лучше, чем повторный запуск на глазах комиссии.
- Нет сети: сценарий CON-003 работает локально, кроме клона публичного
  репозитория. Клон уже сделан, повторный прогон берёт свежий клон с GitHub.

## Вопросы, к которым быть готовым

- **Чем это отличается от Dependabot?** Dependabot смотрит только зависимости;
  здесь три класса проверок, единая модель находок, политика по уровням,
  baseline, исключения и вердикт, который блокирует пайплайн.
- **Почему 11 алертов Dependabot закрыты?** Все они относятся к учебному
  `demo/requirements.txt`, в приложении этих версий нет. Подробности в
  `docs/demo.md`.
- **Почему не блокирует всё подряд?** Политика по severity, baseline для
  исторического шума, исключения с причиной и сроком.
- **Как масштабируется?** Очередь RQ: API только принимает задачу, worker
  обрабатывает; воркеров можно добавить.
- **Что с секретами?** В базе только SHA-256, открытое значение показывается
  один раз, в находках маскируется на нормализации.
