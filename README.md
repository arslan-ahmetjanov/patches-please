# Security Gate

Информационная система автоматизированного контроля безопасности разработки (Security Gate) для CI/CD-конвейера.

Дипломный проект — ВКР по направлению 09.03.03 «Прикладная информатика», УГНТУ.

## Что делает система

Встраивается в пайплайн, запускает проверки безопасности (SAST, секреты, уязвимые зависимости и образы), приводит результаты к единой модели, применяет политику проекта и блокирует переход релиза на следующий этап при критических находках. Ведёт историю прогонов и показывает метрики.

## Источник темы

Тема взята из открытого запроса корпорации на площадка пилотных запросов: «Автоматизированная система контроля безопасности разработки (Security Gate)», заказчик — страховая компания. Карточка запроса, цитата и маппинг на требования — в `docs/source-request.md`.

## Статус

Спецификация V1 зафиксирована. Реализация идёт по этапам `specs/security-gate-mvp/tasks.md`: выполнен этап 1 — скелет проекта (T-001), из этапа 2 закрыты подключение к PostgreSQL и первая миграция (T-002), общие фикстуры тестов и CI (T-003), вход и выход с cookie-сессией (T-004).

## Быстрый старт

Нужны Docker Compose и [uv](https://docs.astral.sh/uv/).

```bash
uv sync                        # зависимости для локальных тестов и линта
cp .env.example .env           # параметры локального стенда
docker compose up -d --build   # postgres, redis, api, worker
curl http://localhost:8000/health
```

Ожидаемый ответ: `{"status":"ok"}`. Остановка стека — `docker compose down`.
Подробный runbook развёртывания с нуля появится в задаче T-033.

## Вход в интерфейс

Вход работает в двух видах на одном сервисе: REST API для программ и HTML-форма
для браузера. Оба используют cookie-сессию `security_gate_session` (HttpOnly,
SameSite=Lax, Path=/, срок 7 дней).

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | JSON `{"email", "password"}` → 200, пользователь `{id, email, role}` и Set-Cookie; неверные данные — 401 |
| POST | `/api/v1/auth/logout` | 204, закрывает сессию и очищает cookie |
| GET | `/login` | страница входа |
| POST | `/login` | форма входа: успех — 303 на `/projects`, ошибка — 401 с сообщением |
| POST | `/logout` | 303 на `/login` |

Пароль хранится только хешем `scrypt` (n=2¹⁴, r=8, p=1, соль 16 байт), сессия —
хешем SHA-256 токена. Открытые пароли и токены в базу и логи не попадают.
Неверный пароль и неизвестный email дают одинаковый ответ 401, чтобы не раскрывать
наличие учётной записи. Регистрации пока нет: учётные записи создаёт сервисная
функция `create_user`, первого пользователя заведёт демо-сев (T-032).

Флаг `secure` у cookie выключен для локального стенда по HTTP; для демо-стенда
за HTTPS он включается вместе с формами и CSRF в T-024.

## База данных и миграции

Схема хранится в PostgreSQL 16, изменения — в миграциях Alembic. Строка подключения
одна на всё: переменная `DATABASE_URL`. Контейнеры `api` и `worker` получают её из
`docker-compose.yml` (хост `postgres`), а миграции с хоста запускаются без переменной
и по умолчанию идут на `localhost:5432` — значение задано в `app/db.py`.

Если меняли пароль или порт PostgreSQL в `.env`, передайте `DATABASE_URL` и при
миграциях с хоста:

```bash
# bash, Git Bash, WSL
DATABASE_URL=postgresql+psycopg://security_gate:пароль@localhost:5432/security_gate \
  uv run alembic upgrade head
```

```powershell
# PowerShell
$env:DATABASE_URL = "postgresql+psycopg://security_gate:пароль@localhost:5432/security_gate"
uv run alembic upgrade head
```

Команды:

```bash
docker compose up -d          # PostgreSQL должна быть запущена и здорова
uv run alembic upgrade head   # применить все миграции
uv run alembic downgrade -1   # откатить одну миграцию
uv run alembic check          # модели и схема БД не расходятся
```

Первая миграция `migrations/versions/0001_users_sessions.py` создаёт таблицы `users`
и `sessions` по разделу «Данные и контракты» плана. Проверки: `tests/test_migrations.py`
прогоняет upgrade и downgrade без базы (Alembic генерирует SQL в офлайн-режиме),
`tests/test_db.py` — интеграционный тест, ему нужен поднятый стек и применённые миграции.

Комментарии в `alembic.ini` оставлены на английском намеренно: Alembic читает файл
в кодировке системы, и кириллица ломает миграции на Windows.

## Тесты

```bash
uv run pytest -m "not integration"   # быстрые тесты, база не нужна
uv run pytest -m integration         # нужен поднятый стек: docker compose up -d
```

Интеграционные тесты работают с отдельной базой `security_gate_test`. Готовить её
вручную не нужно: фикстуры `tests/conftest.py` создают базу при первом обращении,
применяют миграции Alembic и откатывают изменения после каждого теста. Сервер и
учётные данные берутся из `DATABASE_URL` (по умолчанию — локальный `localhost:5432`),
имя базы заменяется на тестовое; полный URL можно задать через `TEST_DATABASE_URL`.
База стенда при прогоне тестов не меняется.

Линт, формат и типы:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy app
```

## Непрерывная интеграция

Workflow `.github/workflows/ci.yml` запускается на каждый push и pull request.
Job `quality` проверяет формат, линт, типы и быстрые тесты, job `integration`
поднимает `postgres:16` и гоняет интеграционные тесты (тестовую базу и миграции
готовят фикстуры). Версия Python берётся из `.python-version`. Секреты GitHub не
нужны: в workflow используется только локальный пароль сервисной базы
`security_gate_local`.
