# Patches, Please

Информационная система автоматизированного контроля безопасности разработки (Patches, Please) для CI/CD-конвейера: встраивается в пайплайн, запускает проверки, приводит находки к единой модели и блокирует переход релиза на следующий этап при критических уязвимостях.

Дипломный проект — ВКР по направлению 09.03.03 «Прикладная информатика», УГНТУ, группа БИЦз-22-01, 2026.

## Что делает система

Встраивается в пайплайн, запускает проверки безопасности (SAST, секреты, уязвимые зависимости и образы), приводит результаты к единой модели, применяет политику проекта и блокирует переход релиза на следующий этап при критических находках. Ведёт историю прогонов и показывает метрики.

## Что внутри

- **Вход и сессии** — REST API и HTML-форма на одном сервисе, cookie-сессия, пароль хранится только хешем `scrypt`.
- **Проекты** — объект проверки с изоляцией по членству: пользователь видит только проекты, где он участник.
- **Токены CI** — ключи `pp_…` для пайплайнов: открытое значение показывается один раз, в базе лежит SHA-256, отзыв мягкий.
- **Прогоны** — `POST /api/v1/scans` с токеном проекта пишет прогон в очередь, `GET /api/v1/scans/{scan_id}` отдаёт статус для поллинга.
- **Очередь и воркер** — Redis + RQ, отдельный процесс `worker`, healthcheck по регистрации обработчика в очереди.
- **Миграции** — Alembic, четыре обратимые миграции: пользователи и сессии, проекты и членство, токены, прогоны.
- **Спецификация** — разработка по SDD: `specs/patches-please-mvp` (спека, план, задачи с трассировкой к требованиям).
- **Контракт** — `contracts/openapi.yaml` генерируется из `app.openapi()`; тест сверяет файл с живым `/openapi.json`, сверка входит в CI (T-007).

## Быстрый старт

Нужны Docker Compose и [uv](https://docs.astral.sh/uv/).

```bash
uv sync                        # зависимости для локальных тестов и линта
cp .env.example .env           # параметры локального стенда
docker compose up -d --build   # postgres, redis, api, worker
curl http://localhost:8000/health
```

Ожидаемый ответ: `{"status":"ok"}`. Остановка стека — `docker compose down`.
Подробный runbook развёртывания с нуля появится в задаче T-033.

## Вход в интерфейс

Вход работает в двух видах на одном сервисе: REST API для программ и HTML-форма
для браузера. Оба используют cookie-сессию `pp_session` (HttpOnly,
SameSite=Lax, Path=/, срок 7 дней).

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | JSON `{"email", "password"}` → 200, пользователь `{id, email, role}` и Set-Cookie; неверные данные — 401 |
| POST | `/api/v1/auth/logout` | 204, закрывает сессию и очищает cookie |
| GET | `/login` | страница входа |
| POST | `/login` | форма входа: успех — 303 на `/projects`, ошибка — 401 с сообщением |
| POST | `/logout` | 303 на `/login` |

Пароль хранится только хешем `scrypt` (n=2¹⁴, r=8, p=1, соль 16 байт), сессия —
хешем SHA-256 токена. Открытые пароли и токены в базу и логи не попадают.
Неверный пароль и неизвестный email дают одинаковый ответ 401, чтобы не раскрывать
наличие учётной записи. Регистрации пока нет: учётные записи создаёт сервисная
функция `create_user`, первого пользователя заведёт демо-сев (T-032).

Флаг `secure` у cookie включается вне локального стенда: при `APP_ENV=local`
или пустом значении стенд работает по HTTP, при любом другом — по HTTPS.
Формы настроек проекта защищены CSRF-токеном: double-submit cookie `pp_csrf`
и скрытое поле `csrf_token` сверяются на сервере.

## Проекты

Проект — объект проверки: название, slug, адрес репозитория и ветка по умолчанию.
Видимость проектов определяется членством: пользователь видит только те проекты,
где он участник. Создатель проекта сразу получает членство с ролью `owner`.

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/v1/projects` | JSON-список своих проектов; без сессии — 401 |
| POST | `/api/v1/projects` | создаёт проект и членство `owner`, отвечает 201; занятый slug — 409 |
| GET | `/projects` | страница со списком своих проектов и формой создания |
| POST | `/projects` | форма создания: успех — 303 на `/projects`, ошибка — та же страница с сообщением |

Slug вводится вручную: строчные латинские буквы, цифры и дефис, от 2 до 100
символов. Название — до 200 символов, `repo_url` необязателен, `default_branch`
по умолчанию `main`. Создавать проекты может любой аутентифицированный
пользователь. Роли членства (`owner`/`member`) станут основой проверки прав в T-025.

## Токены проектов

Токен — ключ, которым CI подтверждает право на проект и запускает прогоны.
Открытое значение показывается один раз — в ответе на создание;
в базе хранится только SHA-256. Отзыв мягкий: токен помечается недействительным,
но остаётся в истории.

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/v1/projects/{project_id}/tokens` | список токенов без открытых значений; доступен участнику проекта |
| POST | `/api/v1/projects/{project_id}/tokens` | создаёт токен, отвечает 201 `{id, name, token, created_at}`; только `owner` |
| DELETE | `/api/v1/projects/{project_id}/tokens/{token_id}` | отзывает токен, 204; повторный отзыв тоже 204; только `owner` |

Формат токена — `pp_` и `secrets.token_urlsafe(32)`: префикс отличает токен
Patches, Please от прочих строк. Создавать и отзывать токены может владелец
проекта, участник (`member`) видит список без значений; посторонний получает 404,
чтобы существование чужого проекта не раскрывалось. Проект в пути задаётся UUID.
Страницы управления токенами пока нет: форма появится со страницей проекта
(T-022) или настроек (T-024). Решение и требования —
`specs/patches-please-mvp/delta-002-tokens.md`.

## Прогоны

Прогон — один запуск проверки коммита из CI. Запуск и поллинг идут через REST
API с токеном проекта; отдельной логики под провайдера нет, `provider`
записывается в историю (FR-019).

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/v1/scans` | JSON `{commit_sha, ref, provider}` → 202 с объектом прогона `{id, status, commit_sha, ref, provider, created_at, verdict}` и задача в очереди; без токена — 401 |
| GET | `/api/v1/scans/{scan_id}` | статус прогона для поллинга; чужой или несуществующий — 404, без токена — 401 |

Доступ — `Authorization: Bearer pp_...`: cookie-сессия интерфейса прогоны не
открывает, она появится на чтении вместе со страницами (T-022, T-025).
`provider` принимает `github` или `gitlab`, `commit_sha` — полный SHA-1 или
SHA-256 в нижнем регистре, `ref` — Git ref без пробелов (`main`,
`refs/heads/main`, `refs/pull/1/head`). Повторный запрос с тем же проектом и
коммитом возвращает существующий прогон: второй строки и второй задачи не
появляется. Прогон создаётся со статусом `queued`; воркер фиксирует приём задачи (T-008,
T-009), адаптеры трёх сканеров и отдельный офлайн-образ worker готовы
(T-011…T-013), подключение сканеров к обработчику — следующие задачи.

## Контракт REST API

Контракт лежит в `contracts/openapi.yaml`, но источник правды — приложение:
файл генерируется из `app.openapi()`, а не правится вручную. Файл описывает
пути, методы, коды ответов, `operationId`, параметры и все схемы запросов и
ответов. Живая схема доступна по `/openapi.json` на запущенном сервисе.

```bash
uv run python -m scripts.export_openapi      # перегенерировать contracts/openapi.yaml
uv run pytest tests/test_contract.py         # сверить файл с приложением
```

Сверка идёт без исключений: тест сравнивает файл с живой схемой целиком и
дополнительно проверяет структуру — уникальность `operationId`, наличие
ответов, разрешимость всех `$ref` и объявленные path-параметры. Этот же тест
входит в job `quality` CI, поэтому расхождение видно до слияния.

В контракте две схемы безопасности. `cookieAuth` — cookie-сессия
`pp_session`; она требуется на операциях проектов и токенов.
`bearerAuth` — токен проекта (`Authorization: Bearer pp_...`); он требуется
на запуске прогона и поллинге статуса.
Ответ 422 перечисляет только `type`, `loc` и `msg` — ровно то, что отдаёт
обработчик в `patches_please/main.py`; присланные значения в ответ не попадают.

## База данных и миграции

Схема хранится в PostgreSQL 16, изменения — в миграциях Alembic. Строка подключения
одна на всё: переменная `DATABASE_URL`. Контейнеры `api` и `worker` получают её из
`docker-compose.yml` (хост `postgres`), а миграции с хоста запускаются без переменной
и по умолчанию идут на `localhost:5432` — значение задано в `patches_please/db.py`.

Если меняли пароль или порт PostgreSQL в `.env`, передайте `DATABASE_URL` и при
миграциях с хоста:

```bash
# bash, Git Bash, WSL
DATABASE_URL=postgresql+psycopg://patches_please:пароль@localhost:5432/patches_please \
  uv run alembic upgrade head
```

```powershell
# PowerShell
$env:DATABASE_URL = "postgresql+psycopg://patches_please:пароль@localhost:5432/patches_please"
uv run alembic upgrade head
```

Команды:

```bash
docker compose up -d          # PostgreSQL должна быть запущена и здорова
uv run alembic upgrade head   # применить все миграции
uv run alembic downgrade -1   # откатить одну миграцию
uv run alembic check          # модели и схема БД не расходятся
```

Первая миграция `patches_please/migrations/versions/0001_users_sessions.py` создаёт таблицы `users`
и `sessions` по разделу «Данные и контракты» плана, вторая
`0002_projects_members.py` — `projects` и `project_members` (T-005), третья
`0003_project_tokens.py` — `project_tokens` (T-006). Все обратимы:
`downgrade` удаляет таблицы в порядке, обратном созданию. Проверки:
`tests/test_migrations.py` прогоняет upgrade и downgrade без базы (Alembic генерирует
SQL в офлайн-режиме), `tests/test_db.py` — интеграционный тест, ему нужен поднятый
стек и применённые миграции.

Комментарии в `alembic.ini` оставлены на английском намеренно: Alembic читает файл
в кодировке системы, и кириллица ломает миграции на Windows.

## Тесты

```bash
uv run pytest -m "not integration"   # быстрые тесты, база не нужна
uv run pytest -m integration         # нужен поднятый стек: docker compose up -d
```

Интеграционные тесты работают с отдельной базой `patches_please_test`. Готовить её
вручную не нужно: фикстуры `tests/conftest.py` создают базу при первом обращении,
применяют миграции Alembic и откатывают изменения после каждого теста. Сервер и
учётные данные берутся из `DATABASE_URL` (по умолчанию — локальный `localhost:5432`),
имя базы заменяется на тестовое; полный URL можно задать через `TEST_DATABASE_URL`.
База стенда при прогоне тестов не меняется.

Линт, формат и типы:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy patches_please
```

Короткие команды лежат в `Makefile`: `make up`, `make test`, `make lint`,
`make type`, `make check` (линт + типы + быстрые тесты), `make migrate`.

## Непрерывная интеграция

Workflow `.github/workflows/ci.yml` запускается на каждый push и pull request.
Job `quality` проверяет формат, линт, типы, контракт OpenAPI и быстрые тесты,
job `integration` поднимает `postgres:16` и гоняет интеграционные тесты (тестовую
базу и миграции готовят фикстуры). Версия Python берётся из `.python-version`.
Секреты GitHub не нужны: в workflow используется только локальный пароль
сервисной базы `patches_please_local`.

## Известные ограничения

- Политики, вердикта и отчётов в коде пока нет: это задачи T-014…T-033. Сканеры и нормализация SARIF готовы (T-011…T-013).
- Прогон принимается и ставится в очередь, задача воркера переводит его в `running`; сканеры к обработчику ещё не подключены — это T-014 и позже.
- Регистрации нет — учётные записи создаёт сервисная функция `create_user`.
- Локальный стенд работает по HTTP; `Secure` у cookie сессии и CSRF включается при `APP_ENV`, отличном от `local`.
- Страницы управления токенами нет: токены создаются через REST API.
- Демо-репозитория с внедрёнными уязвимостями (T-032) и runbook развёртывания (T-033) пока нет.
